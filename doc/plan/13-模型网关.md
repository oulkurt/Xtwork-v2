# 13 模型网关与小瞳多渠道模型平面

> 目标：为内置助手「**小瞳**」（`xtworkPi`）统一提供**企业微信公司团队渠道**与 **19 类成员模型供应商（16 类 4 协议 API 渠道 + 3 类 OAuth 订阅渠道）**，在零协议损耗的前提下守住「真实凭据绝不进入 Pi、Bash、WebView 与明文配置文件」的安全边界。
>
> 相关 [01 架构](01-架构.md) · [03 内置运行时](03-内置运行时-Pi.md) · [08 通用任务化](08-通用任务化改造.md) · [10 里程碑](10-里程碑与验收.md) · [ADR-008](../decisions/008-model-gateway.md) · [ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md)

## 1. 演进方向（【已定】2026-11-25 确认，见 ADR-012）

M0 预览阶段已验证单路由 `openai-completions` 网关（`xtwork/standard` → Magpie / 自定义 Chat Completions）。按 [ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md)，M1b 将模型平面升级为与 Electron 版 `xiaotong_work` 能力对齐的双轨模型供给：

| 渠道类别 | 认证与来源 | 线协议 | 用户体验 |
|---|---|---|---|
| **公司团队渠道**（`xiaotong-work-team`） | Keycloak OIDC + PKCE (`S256`, `kc_idp_hint=wecom-web`) 企业微信扫码 → JWKS `RS256` 校验 → `/api/oauth/exchange/keycloak` 换取个人长效 `sk-` Key | `openai-completions`（`https://llm-api.sci-it.com/v1`） | 扫码即用，默认选中 `deepseek-flash`，自动同步 `/v1/models`；不可篡改服务地址/凭据或删除 |
| **16 类成员 API 渠道** | 成员自带 API Key（含智谱团队版复合凭据 `apiKey; org; project`） | 保协议透传 4 种原生协议：`anthropic-messages`、`openai-completions`、`openai-responses`、`google-generative-ai` | 覆盖 Anthropic、OpenAI、OpenAI Responses、DeepSeek、Google、Kimi API / Coding Plan、智谱 AI / Coding Plan / 团队版、火山引擎 API、MiniMax、通义千问 / Token Plan、小米 MiMo API / Token Plan 及自定义端点 |
| **3 类成员 OAuth 订阅渠道** | 浏览器 OAuth / RFC 8628 Device Code + 二维码，60s 提前续期 + 串行刷新锁 | ChatGPT Codex (`openai-codex-responses`)、GitHub Copilot、xAI (Grok) | 无需手填 API Key，支持 Copilot 组织/订阅级模型过滤与 Codex/Copilot 窗口额度展示 |
| **开发测试兜底线路** | 环境变量 `XTWORK_MODEL_UPSTREAM_URL` / `MODEL` / `KEY_FILE` | `openai-completions` | 保留给本地 Magpie 冒烟与离线 E2E 自动化测试 |

## 2. 接口、协议保真与进程边界

```text
聊天框 → T3 服务端 ──Pi RPC──▶ 小瞳（随包 Pi CLI）──HTTP + SSE（4 种原生协议）──▶ 本机保协议网关 → 公司 / 19 类供应商
                    │               │                                                    ▲
                    ├── MCP ────────┤                                            OS 钥匙串（fail-closed）
                    │     ├─ 插件宿主（待办/日程/笔记）                          app.xtwork.model-channels
                    │     └─ delegate_task → 外部 Coding Agent（独立认证）
```

- **为什么采用「保协议反向代理」而非单协议转译**：
  - 将 19 类供应商全部转译为 `POST /v1/chat/completions` 会丢失 Anthropic adaptive thinking 与 prompt caching、OpenAI Responses reasoning items、Google Gemini 原生多模态思考与厂商特有字段。
  - 新网关按 `/c/<channelId>/<apiKind>/*` 暴露 4 种原生协议端点；随包 Pi 仍通过 `@earendil-works/pi-ai` 使用原生协议栈对话，网关仅负责校验 `XTWORK_MODEL_GATEWAY_TOKEN`、查内存路由表、注入上游认证头（`x-api-key` 或 `Authorization: Bearer`）、注入 Coding/Token Plan 必需的 `User-Agent`、执行少量已验证的请求体补丁（如 DeepSeek V4 Anthropic 端点的 `output_config.effort`）并原样流式透传 SSE。
- **3 类 OAuth 订阅渠道的统一 Proxy-Only 边界（M1b-Gate 1 必过探针）**：
  - 坚持**统一 Proxy-Only 不变量**（真实 `access_token` 与 `refresh_token` 均绝不进入 Pi 内存或 `runtime/pi/` 磁盘，不采用把真实 `access_token` 注入 Pi 内存的折中方案）。
  - 针对随包 Pi `1.5.2` 已静态核实的传输约束（Codex 联网前解析 `chatgpt_account_id` 且默认先尝试 WebSocket；Copilot `toAuth` 会生成凭据相关 `baseUrl`），在薄适配层提供**网关感知 auth/transport 适配**（明确 Codex HTTP/SSE 策略与无密文占位账户字段、覆写 Copilot `baseUrl` 并由服务端/网关双重强制 `availableModelIds` 过滤、xAI 串行刷新），在 M1b-Gate 1 完成真机探针后再扩展全量 19 类供应商。

## 3. 稳定模型 ID、零渠道态与活跃 Pi 会话热刷新

- **稳定模型 ID 与网关白名单**：放弃写死的 `--provider xtwork --model standard`，改用 `<channelId>/<modelId>`（公司渠道为 `xiaotong-work-team/<modelId>`）以支持同厂商多账号并存；网关在转发前强制校验渠道与模型的启用白名单；零渠道或删除当前选中渠道时平滑回落到下一个可用模型或待配置引导态。
- **活跃 Pi 会话热刷新合同**（解决 Pi `1.5.2` `rpc-mode.js:387` 内存快照不重读 `models.json` 的断层）：
  1. 渠道变更时，服务端先更新网关内存路由表（进行中的流式请求保留发起时的路由快照），再原子重写 `runtime/pi/models.json`（临时文件 `0600` + `rename`，仅存 `$XTWORK_MODEL_GATEWAY_TOKEN`）；
  2. 调用 `ProviderRegistry.refreshInstance(xtworkPi)` 刷新前端模型选择器；
  3. **同步更新活跃 Pi RPC 会话**：M1b-Gate 1 优先验证随包受信 Pi 扩展提供的可等待 `reload_models` 命令以原子刷新内存 `ModelRegistry`；若 Pi `1.5.2` RPC 限制运行中替换，则在空闲/回合边界按配置版本号 `catalogRevision` 受控重建 Pi 进程并复用原生 `sessionFile` 恢复续聊。
- `runtime/pi/models.json` 与 `runtime/pi/sessions` 继续留在应用私有数据目录；`pi-shell` 在交给 Bash 前剥离 `XTWORK_MODEL_GATEWAY_TOKEN` 与 `T3_MCP_BEARER_TOKEN`。

## 4. 凭据安全、硬化 SecretStore 与合规边界

- **单一硬化 OS SecretStore**：不发展多套凭据库（不复用仅用于浏览器导入的 `@napi-rs/keyring`，也不用单项上限 2560 字节的 `mygo.Secrets`）。抽离并硬化共享 OS 凭据存储模块（`app.xtwork.model-channels` 与 `app.xtwork.im-bridge` 独立命名空间），先补齐 `missing`/`unavailable`/`denied` 错误分类、`delete` 退出码检查与回读确认、fail-closed 零明文回退，以及登出/删除与在途 OAuth 刷新之间的代际栅栏。
- **准确表述安全与注销边界**：OS 钥匙串与环境变量剥离防明文落盘与意外继承，不等同于同 UID 任意用户批准 Bash 的 OS 强沙箱；企业微信本地退出经密钥删除回读验证后立即停止本机调用并尽力撤销 OIDC `refresh_token`，但不等同于服务端撤销 `new-api` 管理员签发的个人长效 `sk-` Key。
- **元数据与密文彻底分离**：`<数据目录>/channels/channels.json`（`0600`）仅保存渠道结构与启用模型，绝不落盘公司或成员密文；前端仅获脱敏状态。
- **企业微信登录安全**：`localhost:49160` 回调严格校验 `Host`、`state`、`nonce`、`code` 唯一性、JWKS `RS256` 签名与 `iss`/`aud`/`azp`，回调页设置 `Cache-Control: no-store`、`Referrer-Policy: no-referrer` 与 nonce CSP 并以 `history.replaceState` 抹除 URL 中的 `code`。
- **诊断日志脱敏**：仅记录时间、请求 ID、渠道 ID、协议族、状态码与耗时；请求正文、回复内容、原始错误中的密钥与回调 URL 一律不得写入日志。
