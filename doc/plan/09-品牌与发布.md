# 09 品牌与发布

【已定】日常界面用自有品牌，内置助手开箱可用。对外发布名、图标和更新域名由 Q-01 决定。

相关：[02 上游与改造层](02-上游与改造层.md) · [03 内置运行时](03-内置运行时-Pi.md) · [10 里程碑与验收](10-里程碑与验收.md)

## 1. 品牌从一份配置生成

构建时由 `overlay/brand/` 生成应用名、图标、Bundle ID、安装器标识、数据目录、URL scheme、更新源和支持链接。桌面壳、Web 标题、设置、任务通知和错误提示使用同一份值。上游的内部包名留在源码和构建工具中。安装标识和数据目录使用 v2 自己的值，方便用户并装和试用。

默认助手在对话和错误页使用「**小瞳**」（按 [ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md) 由旧默认值「内置助手」更名，已于 [PR #24](https://github.com/oulkurt/Xtwork-v2/pull/24) 落地）或产品名称。产品用 Pi 的 `--append-system-prompt` 附加身份与任务说明，沿用上游工具提示。发布验收包含「你是谁」、无模型授权、运行时启动失败和升级后首次对话。

## 2. 自有服务

| 上游出口 | v1 处理 | 验收 |
|---|---|---|
| T3 Connect、Clerk | 移除面向用户的配对与登录入口，关闭对应服务装配 | 首启、设置和空闲状态无相关连接 |
| T3 遥测 | 默认关闭；服务端启动传 `T3CODE_TELEMETRY_ENABLED=false`，发布构建检查其它出口 | 对首启、聊天、退出做一次出站记录 |
| 公开站点、帮助链接 | 指向产品支持地址 | 菜单、关于页和错误页链接可达 |
| 版本更新 | 只查询本产品发布源 | 验证安装后的配置和真实检查请求 |
| Pi 内置模型授权 | 用 [13](13-模型网关.md) 的产品通道 | 测试通过产品凭据进行首轮对话 |

## 3. 制品

- 构建由同一组锁定的版本出发。产物带 mygo 外壳、Node（含随包 `npm`/`npx`，PR #26 已接入）、T3 服务端和界面、锁定的 Pi 包与启动器、`im-bridge` 远程连接服务、插件宿主、内置插件和许可文件。
- 【建议】macOS arm64 先出内部预览版。Windows x64 做独立的端到端验证，包含 Node 启动信息传递、WebView2 和升级。macOS x64、Linux 是否进入首发由 Q-12 决定。
- macOS 发布制品签名、公证再出 DMG。Windows 签名后运行安装和卸载验收。
- 候选更新链路是 [mygo updater](https://mygo.run/docs/plugins/updater.md) 加发布清单。把版本、平台、架构、产物地址和完整性信息作为发布输入。仅当下载校验通过才安装，并在安装前给出可理解的提示。私有预览保留一份可回退的上一版制品，并检查数据兼容。
- 更新地址可以部署到自有发布空间。复用旧 R2 账号或发布脚本属于可选条件，见 [12](12-从xtwork迁移.md)。

## 4. 发布验收

1. 在干净机器安装与冷启动。确认应用自带 Node 和 Pi，再发消息、取消一次生成、创建一条待办并退出。检查 Pi RPC 子进程、服务端和插件宿主均已回收。
2. 依据锁定版本的许可文件生成第三方清单，随安装包提供适用的 LICENSE、NOTICE 和依赖归属（含 `im-bridge/THIRD_PARTY_NOTICES`、`plugin-host/THIRD_PARTY_NOTICES` 与 `LICENSE.Kero`）。关于页提供「开源许可」入口。[T3 Code LICENSE](https://github.com/pingdotgg/t3code/blob/main/LICENSE) · [Pi LICENSE](https://github.com/earendil-works/pi/blob/v1.5.2/LICENSE) · [mygo LICENSE](https://github.com/egoist/mygo/blob/v0.10.0/LICENSE)
3. 检查用户可见文案、进程相关报错和外部请求。第三方归属清单保留来源名称。
4. 从 Dim Alpha 的测试数据副本升级，检查新对话使用 Pi，旧对话、待办和授权设置仍可访问。检查更新包内的 Pi 与第三方归属。校验失败的更新可留在当前版本。
