# 07 远程连接插件

> 【已定】架构与产品范围按 [ADR-011](../decisions/011-mingle-im-bridge.md) 执行（2026-11-24）。复用 [earayu/Mingle](https://github.com/earayu/Mingle)（MIT）的渠道适配器与状态机作为 T3 服务端监管的独立 Node `im-bridge` 服务，首发聚焦 **飞书、个人微信（iLink）、企业微信**，第一版开放私聊与已放行群聊 `@机器人`，并对齐 Mingle 的伴侣体验与硬性安全边界。
>
> 【已定 · Leader 演进】将远程连接统一绑定到 Captain 式「Leader」长期主管实体、在侧栏顶部固定独立 `local_only` 主管入口、按 run 持久化 fail-closed 执行策略以及 Mingle 控制台能力的分级移植契约见 [ADR-013](../decisions/013-leader-supervisory-threads.md)（2026-11-25 经 Astra 6.2 与 Opus 5.5 共识确认）。

用户在手机或电脑的常用 IM 里私聊或 `@机器人` 派活，运行中的小瞳 Work v2 接手任务。只有发给机器人的任务会进入桌面侧栏对话，回到电脑可以打开同一条对话继续做；群里不相关的聊天只作为已放行群的本地背景沉淀，不污染桌面侧栏。

相关章节见 [01 架构](01-架构.md)、[05 插件系统](05-插件系统.md)、[06 待办、日程与笔记](06-内置插件-待办日程笔记.md) 和 [ADR-011](../decisions/011-mingle-im-bridge.md)。

## 1. 产品体验与默认开关的四态生命周期

远程连接作为**内置受信插件**随应用发布，在插件列表与设置页中**默认开关打开（入口可见）**，运行状态严格分为四态：

1. **随包内置 & 界面可见（默认开）**：打开「设置 → 远程连接」或插件列表直接可见，无需额外安装或开启开发者模式。
2. **`idle`（未绑定，默认静默）**：尚未绑定任何 IM 平台前，零外网长连接、零后台轮询、不请求任何系统隐私权限。
3. **`pairing`（临时配对态）**：当接入流程需通过私聊验证码认领 Owner（企业微信扫码/手填凭据、飞书手填凭据、以及飞书扫码缺 `ownerId` 兜底）时，`im-bridge` 建立受限临时连接——**仅接收该连接的 6 位一次性认领码私聊（10 分钟有效，错 5 次作废）**，拒绝其余一切消息且绝不唤醒 T3/Pi；认领完成后才切入 `active`。
4. **`active`（已激活）与 `backgroundRuntime`（绑定后引导）**：认领后开放正常任务收发；首次绑定成功后引导用户开启「关窗后托盘常驻 / 开机自启 / 插电保持唤醒」（收口 `Q-07`）。

| 用户操作 | 预期体验 |
|---|---|
| 打开「设置 → 远程连接」 | 看到飞书、微信、企微三个首发渠道；点击即可扫码建机器人/扫码登录，或手填已有应用凭据 |
| 认领 Owner | 飞书扫码（返回 `ownerId` 时）、微信扫码直接以扫码人为 Owner；企微、手填凭据及飞书缺 `ownerId` 兜底经 `pairing` 态私聊 6 位验证码认领 |
| 私聊或在已放行群里 `@机器人` | 立即回执（表情/流式卡片/输入状态），在 T3 创建或续聊对应 Thread，桌面侧栏出现该任务并标明 IM 来源；返回原生格式结果 |
| 在桌面打开 IM 群任务继续私有对话 | 默认从该群任务**派生独立本地私有 Thread**（`replyAudience = local_only`），桌面私有对话和工具结果绝不进入原群会话历史；仅当显式选择“发往该群”时留在群会话并受群受众约束 |
| 群里其他人聊天（未 `@` 机器人） | 已放行群的无关聊天存入 `im-bridge` 本地历史缓存作为 `unseen` 背景，**不建 T3 Thread，不出现在桌面侧栏，不消耗模型额度**；未放行/已拒绝的群不入背景检索 |
| 群里或私聊触发高危操作 | 暂停并弹出桌面原生单次确认（仅 Owner 可批准）；不自动放行隔离目录外读盘、本机 Shell、Owner 私有数据跨群读取或跨聊天外发 |
| 追问与并行多任务 | 按回复链、飞书话题（`reply_in_thread`）路由回原任务 T3 Thread；同一群同时派多个任务直接由 T3 并发多 Thread 处理 |
| 在 IM 中发送 `/stop`（仅 Owner） | 立即中止当前任务回合；不暴露 `/new`、`/switch`、threadId 等底层会话命令 |
| 暂停或解绑 | 托盘可一键暂停收发；解绑立即断开连接并清除系统安全凭据库条目，桌面已有历史任务仍可查看 |

## 2. 首发三平台接入（复用 Mingle MIT 渠道层）

基于 `earayu/Mingle@006220e8` 的平台无关 `Channel` / `ChannelConnection` 抽象，首发仅引入 **2 个 MIT 许可的官方 SDK**（微信零依赖），全部走出站长连接/长轮询，无需公网地址：

| 渠道 | 依赖与源码基线 | 接入与传输 | 群聊与能力边界 | v2 首发策略与待验证项 |
|---|---|---|---|---|
| **飞书** | `@larksuiteoapi/node-sdk@1.76.0`（MIT）；复用 `feishu.ts` | 扫码建应用（浏览器打开授权页亦可）或填 App ID / Secret；官方 WebSocket 长连接 | 支持私聊 + 群 `@` + 话题回复（`reply_in_thread`）+ 流式卡片 + 表情回执 + 图片/文件；**未 `@` 群背景、其他机器人消息、成员资料、文档评论需二次扫码补权** | **首发基准渠道（Mingle 已有真机验证）。** ① 恢复**单 App 单活约束**：同一飞书自建应用多客户端接入时事件随机投递，首版每台 Xtwork 实例独立配置应用；② 保留每连接独立 `DefaultCache` 防止同进程不同机器人同群丢消息；③ 扫码缺少 `ownerId` 时自动走 `pairing` 验证码认领 |
| **企业微信** | `@wecom/aibot-node-sdk@1.0.7`（MIT）；复用 `wecom.ts` | 手机企业微信扫码建智能机器人或填 Bot ID / Secret；官方 WebSocket 长连接 | 支持私聊 + **群 `@`（官方只推送 `@` 消息，无未 `@` 群背景）** + Markdown 原生流式回复（9 分钟窗口交接 + 主动发送兜底）+ 图片/文件；无表情与话题 | **重点首发渠道（需在 v2 完成真机端到端验收）。** 接入后经 `pairing` 态认领 Owner；需真机实测长连接重连、多端连接挤占及 >9 分钟长任务切换主动发送 |
| **个人微信** | **零外部 npm 依赖**（纯 `fetch` + `node:crypto`）；复用 `wechat.ts`（源自 `dsh-im` MIT） | 微信扫码授权（含可能的手机验证码/实名 PIN）；腾讯 iLink（`ilinkai.weixin.qq.com`）HTTPS 长轮询 | **首发先验收私聊闭环**（文本、"正在输入"回执、AES-128-ECB CDN 图片/文件、多微信号 `local_token_list`）；群聊能力视平台真机实测后再定 | **重点首发渠道（需真机与合规实测）。** 强制先将入站消息及去重记录落盘到 `im.db`，再提交并持久化 `getupdates` 游标；必须实测扫码、实名/PIN、主动发送限制、过期凭据恢复，并确认第三方产品分发合规边界 |

## 3. 进程架构、消息流与伴侣范式

```text
飞书 / 微信(iLink) / 企业微信（出站长连接 / 长轮询）
  ↕ 官方接口
im-bridge（T3 用随包 Node 26.13.1 启动的独立子进程，mygo 传入绝对入口路径）
  ├─ Mingle MIT Channel 适配器（feishu / wechat / wecom）
  ├─ 显式状态机：连接(link.ts)、入站(inbound.ts)、门禁(access.ts)、配对(pairing)
  ├─ 凭据存储：仅系统安全凭据库(macOS Keychain / Windows DPAPI / Linux Secret Service，无明文回退)
  └─ 轻量 SQLite（<数据目录>/im/im.db）：去重、微信游标、已放行群背景(FTS5)、通讯录(contacts/people)、Thread 路由
  ↕ 双向 JSONL / loopback IPC（启动执行 hello 版本握手）
T3 服务端（overlay/files/apps/server/src/im/ 薄桥接层）
  ├─ 唯一编排与持久化（statev2.sqlite）：端到端幂等键 → 只为发给机器人的任务建/续 Thread
  ├─ 回合可信上下文（TurnExecutionContext）：绑定发起人、连接、来源、回复受众与隔离工作目录
  ├─ 分层伴侣目录（<数据目录>/companion/）：公开 ROLE.md + private/（跨私聊共享）+ groups/<chatKey>/（群独立）
  ├─ 双层安全闸门：Provider 原生工具钩子（隔离目录外读写与 bash）+ MCP 作用域/私有数据审批
  └─ 内置 MCP 服务：暴露受控 im__* 工具 + 作用域隔离的 todo__* / calendar__* / obsidian__* 工具
  ↕ Pi RPC（首版默认；其他 Provider 达到同等工具隔离边界后开放）
内置助手 Pi
```

### 3.1 消息进出、端到端幂等与状态机

1. **配对态拦截**：连接处于 `pairing` 态时，仅校验私聊中的 6 位认领码，其他消息一律忽略，不入库背景也不唤醒 T3。
2. **门禁优先，再决定入背景或触发**：
   - 入站消息按 `(connection_id, platform_msg_id)` 去重，先经 `access.ts` 纯函数 `gate()` 判定：
     - Owner 永远放行；被拒绝（`blocked`）的群与联系人静默丢弃（`drop`），**不入背景缓存、不参与检索**；
     - 未放行的新人/新群挂起为 `held`，仅保存待审阅的触发消息通知 Owner 在桌面允许或拒绝；
     - 仅**已放行群**中未 `@` 机器人且不属于话题跟进的聊天，才写入 `im.db` 记为 `ignored` 并计入 `unseen`，**不建 T3 Thread、不进桌面侧栏、不调模型**。
3. **端到端幂等、崩溃补投与游标顺序**：
   - 入站消息先经门禁分类落盘：**仅通过门禁、应交给 T3 处理的触发消息**以 `received` 状态进入待投递队列（未放行记 `held`，已拒绝记 `blocked` 并丢弃，已放行群的无关背景记 `ignored`），再携带稳定幂等键 `im:<connectionId>:<platformMsgId>` 投递给 T3。
   - T3 在创建/追加回合时原子持久化该幂等键并返回 `(threadId, turnId)` 确认，`im-bridge` 收到确认后将记录标为已受理；若在落盘后、T3 受理或确认前崩溃，`im-bridge` 重启时**只扫描已通过门禁且未获 T3 确认的 `received` / `delivered` 触发记录**按同一幂等键补投，T3 幂等返回既有 `(threadId, turnId)`，保证**同一外部消息最多创建一个 T3 回合**，且绝不把 `held` / `blocked` / `ignored` 误投给 T3。
   - **工具写入去重边界**：同一回合内 MCP 重发受 `operationKey` 去重；若回合已进入执行中后进程异常中断，重启后**不自动盲重跑该回合**（桌面标为中断供用户核对，或由写工具层按 `(turnId, toolCallId)` 幂等保护），防止重复创建待办。
   - **微信游标提交顺序**：`wechat.ts` 必须先把本批拉取到的消息经门禁按真实状态分类（仅通过门禁的触发消息记 `received`）并与去重记录一起落盘到 `im.db`，再提交并持久化下一轮 `getupdates` 游标；结合上述启动补投扫描，确保消息既不丢失、不越权放行也不重复建回合。
4. **Thread 路由与并发**：
   - 私聊：沿用连续对话映射；
   - 群聊：按回复链或飞书话题（`reply_in_thread`）映射回已有任务 Thread，否则新建独立隔离工作目录的 T3 Thread；同一群同时派多个任务直接由 T3 并发多 Thread 执行。
5. **对齐 Mingle 伴侣范式**：
   - **消息格式**：沿用 Mingle 结构化消息头与 200 字引用预览；附件不自动落盘，助手按需通过受控工具下载到当前任务的隔离工作目录。
   - **分层伴侣记忆**：
     - `companion/ROLE.md`：公开人格，私聊与群聊共享；
     - `companion/private/`（`MEMORY.md` + `notes/`，64 KB 软上限 + 空闲 `tidy`）：Owner 跨飞书/微信/企微私聊共享同一份记忆；
     - `companion/groups/<chatKey>/`（`MEMORY.md` + `notes/`）：各群独立记忆，避免把 Owner 私聊内容自动注入公司群（需要某群共享全部私聊记忆时，由 Owner 按群显式开启并确认风险）。
   - **通讯录与人物**：支持 `contacts` 短 ID（`u7k2p`）与跨 IM 显式人物关联 `people`（`p3` + 上限 2 KB 备注，新会话首次发言注入 600 字 `peer card`）；严格遵守「Agent 关联不传递权限，Owner 账号只能由 Owner 在桌面关联」。
   - **可选群旁听（M4.4 后续能力）**：默认关闭；按群显式授权启用后须说明额外模型开销，且**旁听评估绝不创建桌面侧栏 Thread**。
6. **出站与原生呈现**：助手回复经受控 MCP 工具或回合终态回写到 `im-bridge`，由适配器原生渲染（飞书流式卡片 + 表情回执、企微流式回复、微信分段文本 + 输入状态）。

### 3.2 断线、睡眠与重启恢复

- **显式连接状态机（`link.ts`）**：所有非终态必有出路——网络/临时错误自动指数退避重连（`5s → 15s → 30s → 1m → 2m → 5m`），凭据失效或权限被撤转入「待用户处理」并明确提示原因与重连/补权限入口。每次连接尝试带递增代号，丢弃过期异步回调。
- **睡眠醒来强重连**：`im-bridge` 每 15 秒检查时钟漂移，间隔超出预期 1 分钟以上即判定系统休眠过，立刻关闭并重连全部活跃通道。
- **发送失败与优雅退出**：明确发送失败最多重试 3 次，结果不确定（`uncertain`）时不自动重发并在桌面标记「送达失败」供手动重试；应用退出时 T3 先优雅关闭 `im-bridge` 断开长连接，验收零残留子进程。

## 4. 群聊安全、危险操作审批与提示词注入防御

第一版开放私聊与已放行群聊的完整任务协作能力，安全底线由**回合可信上下文 + 双层硬闸门 + 提示词注入四层防御**共同保障：

### 4.1 回合级可信上下文、受众隔离与审批策略

授权不依赖消息正文标签，而由服务端为**每个回合**不可变绑定 `TurnExecutionContext`（`source`、`connectionId`、`chatId`、`chatKind`、`senderRole`、`replyAudience`），并严格按受众隔离会话历史：**同一 Provider 会话绝不混用 `local_only`/`owner_dm` 与 `group` 受众**——在桌面基于群任务继续私有对话时自动派生（fork）独立本地 Thread，防止后续群友在原群追问时读到桌面私有消息或私有工具结果：

| 操作类别 | 覆盖路径（原生工具 + MCP） | 审批与作用域策略 |
|---|---|---|
| **安全只读与当前回复** | 问答总结、读取当前任务的隔离工作目录、读取已放行当前群背景、回复当前来源聊天 | 免审批直接执行 |
| **群共享插件数据** | 本群作用域（`chatKey`）下的共享待办/协作记录 | 已放行群内成员（含 Owner）在群内可完整读写 |
| **Owner 私有插件数据** | Owner 私有待办、日程、已授权 Obsidian 笔记（既有旧记录默认归属 Owner 私有） | **Owner 私聊（`owner_dm`）**按桌面规则正常读写（`confirm: true` 破坏性写仍需批准）；**群受众回合（`group`，含 Owner 本人在群内发言）**一律必须经 Owner 单次批准 |
| **目录外本机文件访问** | **Pi 原生 `read`/`grep`/`find`/`ls`/`write`/`edit` 触及当前任务隔离工作目录之外** | **所有 IM 来源回合（含 Owner 私聊与群聊）及所有 `group` 受众回合（含桌面显式回复到群）**一律必须经 Owner 单次批准（取消锁定版 Pi 对目录外只读工具的自动放行） |
| **危险执行与跨边界外发** | 本机 `bash`/进程执行、向非当前来源聊天/联系人主动发消息、外发本地私有文件、声明 `confirm: true` 的破坏性插件写操作 | **所有 IM 来源回合及 `group` 受众回合**一律必须经 Owner 单次批准 |
| **跨范围记忆写入** | 群聊回合（含直接文件写、记忆工具或 `tidy`）写入 `ROLE.md` 或 `companion/private/` | **必须经 Owner 单次批准** |
| **管理类操作** | `/stop`、暂停/恢复、放行/拒绝群与联系人、关联 Owner 账号、管理连接与凭据 | **仅 Owner 可执行**（非 Owner 直接拒绝） |

- **单次绑定审批**：每次 `request.pending` 绑定 `(turnId, toolName, normalizedArgsHash, replyAudience)` 且仅单次生效（IM 混合回合禁用“本会话允许”）。首版全部回桌面原生确认；后续按 `Q-09` 开放飞书等 IM 互动卡片审批时，连接器必须强校验点击者 `senderId === connection.ownerId`，且桌面与手机并发操作仅首次生效。
- **其他 Provider 准入**：开发者模式下把 IM 路由到非随包 Pi 的其他 Provider 前，该 Provider 适配层必须先满足同等隔离工作目录与原生工具审批边界。

### 4.2 提示词注入四层纵深防御

1. **L1 结构化不可信数据信封**：所有 IM 入站文本、群背景、引用内容、发送者昵称、附件名与联系人备注，在送入模型前统一包裹在显式不可信边界中（转义闭合标签），清晰标注服务端核验后的 `role="owner|member|bot"` 与 `chatKind`，声明信封内文本不可覆盖系统规则。
2. **L2 双层代码硬闸门**：工具审批、隔离目录路径校验、私有/群作用域校验和门禁全部在随包 Pi 权限钩子、T3 MCP 与 `im-bridge` 代码层强制执行，不依赖模型遵守提示词。
3. **L3 全路径防持久化记忆投毒**：私聊记忆（`companion/private/`）与各群记忆（`companion/groups/<chatKey>/`）默认物理隔离，且跨范围写入（无论经文件工具、记忆工具还是 `tidy`）必须经 Owner 单次审批。
4. **L4 严格凭据隔离（零明文回退）**：vendoring `secrets.ts` 时**移除明文 `0600` 文件回退**，安全凭据库不可用或写入校验失败时直接阻断绑定并提示原因；IM 密钥、模型网关令牌和 T3 MCP 令牌进程级隔离，绝不进入模型环境、SQLite、日志或 HTTP 响应。
