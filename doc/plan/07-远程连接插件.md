# 07 远程连接插件

用户在手机上给机器人发一条消息，运行中的 xtwork_v2 接手任务。回到电脑可以打开同一条对话继续做。飞书、企业微信、微信、钉钉是候选渠道，首发渠道和各渠道开放的操作由产品讨论确定。平台资料核对日期为 2026-11-19，以下平台能力仍需在 xtwork_v2 用测试账号端到端验证。

相关章节见 [01 架构](01-架构.md)、[05 插件系统](05-插件系统.md) 和 [06 待办、日程与笔记](06-内置插件-待办日程笔记.md)。

## 1. 首个可用原型【建议】

先用飞书企业自建应用跑通一个私聊。手机上发「帮我记一下，明天提醒我交差旅报销」，桌面侧边栏出现这条对话，待办里出现一条记录，用户在飞书收到确认。再发「把到期日改到下周一」，Agent 用同一条对话的上下文更新原待办。

| 用户操作 | 原型预期 |
|---|---|
| 桌面打开「设置 → 远程连接 → 飞书」 | 录入自己的应用凭据，看到连接与配对状态 |
| 按桌面提示，在机器人私聊里发一次性配对码 | 桌面显示账号，用户确认后启用这个私聊 |
| 手机发消息 | Agent 开始任务，首条状态反馈为「已收到」，结束时回一条结果 |
| 手机发下一条消息 | 继续当前对话。发送「新对话」可从空白任务开始，是否提供专门命令待原型反馈 |
| 桌面打开该任务 | 看到来源、原始消息、最终结果，可在电脑继续对话 |
| 任务遇到需要许可的操作 | 状态显示「等待确认」，用户可以从桌面处理。平台内审批作为下一步候选，见 §5 |
| 暂停或解绑 | 停止接收新任务和向该渠道发送结果。桌面已有任务仍可查看 |

首个原型只用纯文本和一个私聊。依序验证「绑得上 → 消息确实进了同一个 Agent → 待办确实入库 → 手机收到结果」，再把卡片、第二个渠道和媒体纳入计划。群聊、附件、流式状态、定时主动推送和多设备由后续评审决定。

## 2. 平台接入

| 渠道 | 已有官方路径 | 凭据及传输 | 可验证的候选功能 | v2 判断 |
|---|---|---|---|---|
| 飞书 | 企业自建应用机器人。`im.message.receive_v1` 收消息，`card.action.trigger` 收新版卡片回传，两者均可配置长连接 | 应用 ID、应用密钥。应用需启用机器人，配置事件、所需权限和可用范围后发布。本机发起 WebSocket，常规回复走平台消息 API | 私聊文字、最终回复、互动卡片。卡片回调应在 3 秒内应答 | 首个原型候选。长连接只支持企业自建应用，同一个应用多客户端接入时事件由随机一个客户端接收。首轮给每个 v2 实例单独配应用 |
| 企业微信 | 智能机器人 API 模式。官方长连接可收消息、事件和模板卡片按钮回调，也提供 URL 回调模式 | Bot ID、Secret。本机发起 WebSocket，收消息和发回复使用机器人连接 | 私聊文字、Markdown、流式回复、模板卡片。官方 SDK 要求卡片更新在按钮回调后 5 秒内调用 | 第二个候选。设置指引写清「API 模式 → 使用长连接」。按一个机器人只开一个有效连接配置，新连接会挤掉旧连接 |
| 钉钉 | 开放平台应用机器人，Stream 模式可收机器人消息和互动卡片回调，提供官方 Go SDK | Client ID、Client Secret。应用需要启用机器人、选 Stream 并发布，本机发起 WebSocket | 单聊文字、回复与主动发送、卡片回调。群内消息依赖 @机器人，互动卡片需要关联应用的模板 | 第二个候选，优先级取决于试用者。用事件中的 `sessionWebhook` 快回，并测试其过期后能否通过正式发送 API 送达 |
| 微信 | 腾讯发布了微信渠道插件及 iLink 协议说明，已有官方参照实现可扫码绑定微信机器人并收发消息 | 扫码授权获得机器人凭据，HTTPS 长轮询收取消息，发消息时沿用对应会话的上下文令牌 | 文本收发有官方参照实现。文本之外的媒体、PIN 或实名流程、主动发送和实际账号可用范围分别验证 | 单独做兼容性原型。官方协议文档依据现有插件编写，服务端行为与第三方产品分发条件仍需确认。先验证合规可用的机器人私聊，发布范围保持待定 |

- 飞书的事件和回调在后台分别配置。若要测试按钮，也要订阅相应回调并发布应用。[长连接事件](https://open.feishu.cn/document/ukTMukTMukTM/uYDNxYjL2QTM24iN0EjN/event-subscription-configure-) · [接收回调](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/receive-and-handle-callbacks) · [发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)
- 企业微信以开发者中心的智能机器人协议为准，可以用官方 SDK 快速确认接入行为。[企业微信长连接文档](https://developer.work.weixin.qq.com/document/path/101463) · [企业微信官方 SDK](https://github.com/WecomTeam/aibot-node-sdk)
- 钉钉可从同一个 Stream 客户端分别注册机器人消息和卡片回调，主动发送走平台提供的机器人 API。[钉钉 Stream 协议](https://opensource.dingtalk.com/developerpedia/docs/learn/stream/protocol/) · [官方 Go SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-go) · [卡片教程](https://opensource.dingtalk.com/developerpedia/docs/explore/tutorials/stream/bot/go/card-callback/)
- 微信方案使用机器人会话。当前发布的预览说明还有独立的实名和 PIN 环节，原型应按所选版本实测绑定流程，稳定版与预览版分别记录。[腾讯微信渠道](https://github.com/Tencent/openclaw-weixin/blob/main/README.zh_CN.md) · [iLink 协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md) · [绑定流程预发布说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/release-notes-bot-realname-auth_zh_CN.md)

首发原型按用户自建应用或自行扫码授权设计。产品代管机器人、跨组织分发和自带中继服务都各有单独的发布与权限条件，留到接入体验确定后再决策。

## 3. 进程职责与消息流

```text
手机上的机器人私聊
  ↕ 平台官方接口
Go 插件宿主内的连接器       管连接、凭据、平台事件、收发与限流
  ↕ 受限的宿主能力
moejs 远程连接插件           管消息映射、状态文案和回复格式
  ↕ 插件桥
T3 服务端                  管绑定与任务范围、对话持久化、Agent 请求与事件
  ↕ Pi RPC / MCP
Agent                      使用同一套待办、日程和其他已授权工具
```

1. 连接器把平台消息转成统一的内部事件。最小字段包含 `connectionId`、`chatId`、`senderId`、`messageId`、`receivedAt`、`text`。平台重试 ID 与发回复所需句柄留在宿主。会话和发送者由平台返回的稳定标识识别。
2. 插件桥确认发送者、连接和私聊都已配对，按外部消息 ID 去重，持久接收后尽快给平台应答。大模型耗时独立计算，飞书回调等时限只约束接收处理。
3. 首条消息用 `agent.thread.start` 创建无项目任务，之后用 `agent.thread.send` 进入当前任务。按连接、平台私聊和发送者绑定当前 `threadId`。创建新任务时更新绑定，旧对话可以从桌面打开。
4. `turn.started`、`turn.completed`、`request.pending` 等事件经插件桥投递给对应连接。插件桥按 `threadId` 和来源 `turnId` 确定回哪条消息。桌面主动发起的回合只在本地显示。事件字段和宿主能力草案见 [05 插件系统](05-插件系统.md)。
5. 结果输出后由连接器发回同一个私聊。原型把长结果的摘要发到手机，全文可以在桌面查看。消息包含明确允许外发的结果，已有本地对话及 Obsidian 笔记正文保存在桌面。

Go 侧与各平台 SDK 交互，moejs 只看到标准化事件和受控回复方法。插件可以回复当前来源的任务，收件人由宿主绑定。三个团队平台的长连接与微信轮询共享事件协议，各自保留自己的连接及回复机制。

### 接收与恢复

- 已受理的外部消息去重记录应与 T3 创建回合关联。重推同一条消息时复用现有状态，避免再建一条待办。原型验证 T3 内部入口能否传稳定的命令 ID，以及重启后的查询和对账路径。
- 一个远端对话有回合在执行时，后续消息按收到顺序追加。重启后按已受理状态恢复。执行结果不明时在桌面显示中断，用户可核对任务状态后再继续。
- 连接断开后由连接器退避重连。最终发送失败时，桌面保留结果并标记「送达失败」，可以重试发送已有结果。微信轮询原型需验证接收记录和游标的提交顺序。首轮不依赖单独的消息队列服务。
- 本机服务端要保持在线，桌面关窗后可通过托盘继续运行。睡眠、关机或完全退出时连接离线，各平台恢复时是否补发消息须单独验证。托盘「暂停远程连接」暂时停止收发，设置「解绑」同时清除本地配对。

## 4. 权限与上下文

- 远程连接默认关闭。开通时在桌面本地完成配对，限制为已批准的账号和私聊。配对码短时有效、单次使用。入站消息可携带任意文本，账号与会话的认定来自平台提供的身份和本地配对记录。
- 新任务使用免项目工作区。并发任务的目录隔离按 M1 实测。待办与日程沿用桌面授权和正常工具规则。Obsidian 远端读取、整篇笔记外发、本地项目、终端、第三方外发等能力按产品配置单独开启，首个文本原型只开放验证所需工具。
- Agent 给远端的产出是发到第三方平台的内容。界面在开启时说明这一点，插件只收到关联任务的可转发事件。通知及日志仅记录必要的连接、事件和任务标识，平台密钥及原始凭据存系统钥匙串。
- 原型按「解绑时已开始的任务可在桌面完成，结果留在桌面」验证。用户可在桌面停止当前任务。

## 5. 审批和问题追问【候选】

首个原型使用桌面原生审批。完成文本闭环后再试飞书卡片，把 `request.pending` 中可披露的摘要和有限的选项发到已绑定私聊。用户在手机点确认时，宿主重新核验连接、私聊、点击人和请求有效期，再走 `agent.request.answer`。桌面已处理或超时的请求统一反馈「已处理」或「已过期」。用测试账号验证重复点击、桌面和手机同时操作时只有一个决定生效。

建议把可远端确认的操作限定于产品明确开放的动作，例如对已经绑定的待办执行一次删除。涉及命令执行、文件访问、外发数据以及尚未批准的能力，继续在桌面处理。平台按钮渲染失败时保留任务状态，可回文本「请在桌面确认」。继续开发时再讨论是否支持微信纯文本确认、表单追问、定时主动提醒和模型切换。

## 6. 四个平台的原型验收

| 项目 | 完成条件 |
|---|---|
| 共用闭环 | 已配对手机发送文本，桌面出现同一条任务，Agent 写入一个待办，手机收到一条结果，后续消息接回原任务 |
| 绑定范围 | 未绑定账号和群消息无法创建任务，取消绑定后无法再请求或收结果，旧任务仍可在桌面查看 |
| 重试与断线 | 同一消息的重推只生成一个回合和一条待办。断线重连后可续用，失败的回复有本地记录，重试回信复用结果 |
| 飞书 | 企业自建应用仅用本机出站 WebSocket 收消息。若纳入卡片，在时限内收到可关联的真实按钮回调 |
| 企业微信 | 用 API 模式智能机器人私聊完成真实往返，验证重新连接、账号可用范围和慢任务回复，记录绑定机器人被另一个客户端接管时的状态 |
| 钉钉 | Stream 模式下真实收发单聊。验证快回与慢任务所需的发送接口。若纳入卡片，用已发布应用的模板实测回调 |
| 微信 | 在允许的账号环境验证扫码、收发、重连、解绑与过期凭据恢复。记录所选版本的绑定、主动发送限制及允许分发范围，再决定上线方式 |

原型评审优先确定两个问题。用户最常在哪个平台发起任务，以及是否需要离开电脑后处理审批。决定这两点后再排第二个渠道和卡片功能。群聊里可见的内容、文件传输、远程调用 Obsidian 的开放范围，以及机器人可否主动发定时结果，留给真实试用反馈。
