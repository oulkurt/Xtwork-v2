# 10 里程碑与验收

各阶段的实现进度与已跑过的测试见 [当前进度](../README.md#当前进度)。

【建议】先用一轮本机对话证明桌面壳和助手能配合，再做首页和插件。每个里程碑以可复现的用户操作验收。

## M0 · 跑通桌面、T3 和 Pi

1. 记录 T3、mygo、Node、Pi 的锁定版本，按 [04](04-mygo外壳.md) 启动。
2. 在 macOS arm64 上启动 T3 Node 服务端，mygo WebView 加载本机界面。先验证浏览器模式，再验证生产构建的同源页面、preload 和最小桌面桥接。
3. 用随包 Pi 启动原生 RPC。验证模型发现、首字流式输出、待办 MCP、取消、权限拒绝、自我介绍以及重启后原线程续聊，记录命令、版本和结果。
4. 关闭窗口、重新打开、彻底退出。核对何时保留后台进程。确认显式退出后，这次启动的服务端、Pi RPC 进程、插件宿主和 worker 都已退出。

**通过条件**　新数据目录能首启、收到流式回复、创建待办并在重启后读回。检查一份旧 Alpha 数据的默认设置迁移、对话和待办。Windows 启动信息和子进程管理的验证可以独立进行。

## M1 · 通用任务桌面版

### M1a · 基础通用桌面体验（已完成，PR #19 / PR #20）

- 桌面首启默认进入简体中文（`zh`/`en` 双语切换并持久化）与免项目草稿。
- 普通模式保留内置浏览器（`ServerBrowser` + `/settings/browser` + `⌘⇧J`）、改动对比/检查点、本地文件夹、定时任务、技能与待办；开发者功能开关控制 PR / Issues / Git / Worktree / 终端 / 克隆入口。

### M1b · 内置助手「小瞳」与多渠道模型平面（【已定】见 [ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md)，可与 M1c 并行）

- **Gate 1（前置技术关卡）**：硬化单一共享 OS SecretStore（错误分类 + 删除回读验证 + 并发栅栏）；实跑打通活跃 Pi `1.5.2` 会话热刷新（覆盖新增/改元数据/删当前模型/流式进行中变更）；实跑验证 Proxy-Only 下 Codex / Copilot / xAI 的窄 auth/transport 适配。
- **Gate 2（渠道与网关交付）**：将 `xtworkPi` 更名为「**小瞳**」，升级 `<channelId>/<modelId>` 稳定模型 ID 与零渠道引导；接入**企业微信公司团队渠道**（含 `49160` 端口冲突提示）与基于 Pi `1.5.2` 的**版本化 19 类成员渠道矩阵**及网关启用白名单强制校验。

### M1c · 六大外部编码 Agent、一键安装与 Coding Agent 委派（【已定】见 [ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md)，可与 M1b 并行）

- **Gate 1（工具链、种子实例与授权门禁）**：在 `build-desktop.mjs` 随包携带并校验 `npm`/`npx`，注入服务级 `hostEnvironment`；幂等播种 4 张稳定 ACP 实例卡片（`xtworkKimiCode`、`xtworkQoder`、`xtworkCodebuddyCode`、`xtworkDeepseekHarness`）；在 `AcpRegistrySupport` 与安装入口前落地**服务端统一 Install Consent Gate**，区分受管隔离安装（支持取消/卸载）与官方脚本安装（透明命令预览 + 探针验证）；普通模式开放 `/settings/providers` 及登录终端。
- **Gate 2（Coding Agent 委派合同）**：新增 **Coding Agent 委派设置**（`auto` 或指定外部编码 Agent），通过 T3 原生 `delegate_task` 闭合服务端强制预检（拒绝静默改派）、父项目工作区与非 Git `scratch/` 规则、结构化交接简报、复用父级递归取消，并在打包环境中实跑免项目首条消息委派、普通模式登录、审批等待、进程崩溃恢复以及 **IM/群聊首版硬拒绝外部委派**。

**通过条件**　普通用户安装后，既可通过企业微信扫码或自有供应商直接用「小瞳」完成日常任务，也可经显式授权一键安装并在对话中选用或委派给任一主流 Coding Agent；凭据隔离、活跃会话热刷新、浏览器、中英双语与 IM 硬隔离全部通过打包端到端验收。

## M2 · 插件通路

- Go 插件宿主带一个测试 worker，接通 JSONL 加载、工具调用、授权和停止。
- 插件桥把一个工具接进 Pi 的会话 MCP，并返回插件写入结果。在界面只展示实际已执行的操作。
- 接通一个 @ 上下文条目和一个沙箱面板。核对手工选择、移除、权限拒绝、退出后恢复。
- 核对 MCP 工具是否需要特别暴露、权限是否重复弹窗。用一条测试流程打通确认、拒绝和撤销。
- 冻结这一阶段实际用到的 v2 插件契约和最小夹具。
- 第一阶段补齐 v2 清单强判别、功能与外观双轨注册、结构化诊断，以及基于 `AppRouteModal` 的 `PluginModalHost`。

**通过条件**　同一测试插件能经对话和面板访问同一份状态。重复发送或重试只写一次，禁用插件后新工具调用无法执行。

## M4 · IM 远程连接（飞书、微信 iLink、企业微信）

- 【已定】按 [ADR-011](../decisions/011-mingle-im-bridge.md) 交付 T3 侧独立 Node `im-bridge`（复用 Mingle MIT 渠道层与状态机），首发范围已定为飞书、个人微信（iLink）和企业微信（收口 Q-04）。
- 第一版跑通默认入口可见、静默待机、`pairing` 认领、飞书/企微私聊与已放行群 `@机器人`、个人微信（iLink）私聊闭环、端到端幂等与中断不盲重跑、分层伴侣记忆、Pi 原生目录外读写与私有数据单次桌面审批、以及桌面侧栏只显示任务对话。
- 验收飞书、企业微信、个人微信真机断线重连、休眠醒来重连、崩溃补投幂等、解绑、无全局 Node 打包启动和退出零残留；个人微信（iLink）另须完成实名/PIN、主动发送限制与第三方分发合规验收。IM 内卡片审批待按 Q-09 真机验收后开放。

**通过条件**　同一外部消息（含平台重推与落盘后仅针对已通过门禁触发消息的崩溃补投）最多创建一个 T3 回合，执行中途崩溃的回合不自动盲重跑；群聊与桌面私有历史按受众严格隔离；所有 IM 来源回合及 `group` 受众回合（含桌面显式回复到群）的目录外原生读写、所有 `bash` / 进程执行（无论工作目录）、以及群受众对 Owner 私有数据的访问均需 Owner 单次批准；个人微信（iLink）通过真机与分发合规验收后再正式对外开放；试点功能可随时从桌面暂停或解绑。桌面首发可独立发布，各 IM 渠道通过真机验收后逐个启用。
