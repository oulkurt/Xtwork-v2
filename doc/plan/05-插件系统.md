# 05 插件系统

> 回答：插件由哪些部件组成；插件怎样和 agent 的上下文绑定；插件能做什么、不能做什么；哪些来自 xtwork，哪些是 v2 新增。
> 【已定】功能插件系统用 moejs（内置待办、日程、Obsidian 笔记）；远程连接（IM 接入）按 [ADR-011](../decisions/011-mingle-im-bridge.md) 改由 T3 监管的受信 Node `im-bridge` 提供，保持 `moejs` 沙箱零网络、零凭据边界。（2026-11-24 修订）
> 【建议】插件宿主作为 T3 服务端的子进程运行；每个插件一个 moejs worker 进程。旧实现可作为参考。
> 相关：[01 架构](01-架构.md) · [06 内置插件](06-内置插件-待办日程笔记.md) · [07 远程连接插件](07-远程连接插件.md) · [12 从 xtwork 迁移](12-从xtwork迁移.md)

插件 v2 第一阶段按 [ADR-010](../decisions/010-plugin-v2-runtime.md) 实施。目录与校验统一，功能插件和外观插件分成两条运行轨道。功能插件继续使用 Go 宿主与 worker，外观插件只使用前端声明式应用器。功能视图复用 `AppRouteModal`，外观插件不运行代码。

## 1. 目标与边界

目标：
- 待办、日程、笔记以 moejs 插件形式存在；远程连接作为内置受信服务在界面中统一呈现，并与对话共享上下文（详见 [ADR-011](../decisions/011-mingle-im-bridge.md)）。
- 插件与 agent 的上下文双向绑定：agent 能调用插件；插件能给 agent 提供上下文；插件能观察对话。
- 内置插件与本地插件用同一套机制。内置插件按同一套机制授予基础能力，文件夹和外部连接由用户明确授权。

v1 优先验证内置插件。开发者加载本地测试插件由开发者设置和发布范围决定。
v1 之后：插件分发、AI 生成插件（xtwork 的“插件工坊”）【待定 Q-10】。

不做：
- 插件改动 T3 界面的任意位置。插件只能用第 7 节的槽位。
- 插件直接访问文件系统、网络、进程、凭据。xtwork 的规则继续有效：“插件没有原始文件系统、进程、网络、凭据与网关令牌。”
- 插件之间互相调用。

## 3. 部件

| 部件 | 语言 | 代码位置（规划） | 职责 |
|---|---|---|---|
| 插件桥 | TS | `overlay/packages/plugin-bridge`，挂进服务端 | 启动并监管插件宿主；把插件工具注册进 T3 的 MCP 服务；实现确认流程；把对话事件转给插件；给界面提供插件接口；实现需要服务端参与的宿主能力 |
| 插件槽位 | TS / React | `overlay/packages/plugin-slots`，挂进界面 | 侧栏入口、面板区、命令面板、设置页、输入框 @ 选择器、对话内确认条；在沙箱 iframe 里渲染插件视图 |
| 插件宿主 | Go | `plugin-host/` | 注册表、安装、清单校验、权限裁决、存储、定时回调、worker 监管（IM 远程连接改由 T3 侧独立 Node `im-bridge` 承担，见 [ADR-011](../decisions/011-mingle-im-bridge.md)） |
| 插件 worker | Go + moejs | `plugin-host` 的 worker 子命令 | 在 moejs 沙箱里执行一个插件 |
| 插件 | TS（只用可擦除类型语法）/ JS | `plugins/<id>/` | 业务逻辑、清单、视图文件 |

## 4. 进程与通信

```
界面（React）
 ├─ 插件视图 iframe ──postMessage──▶ 插件槽位（宿主页面）
 └─ 插件槽位 ──HTTP/WebSocket（复用服务端鉴权）──▶ 插件桥
运行时（Pi）──MCP──▶ T3 MCP 服务 ──plugins 工具集──▶ 插件桥
插件桥 ──stdio JSONL（新增 server 角色）──▶ 插件宿主 ──stdio JSONL（plugin 角色）──▶ 每个插件的 worker
T3 IM 桥 ──双向 JSONL / IPC──▶ im-bridge（Node，见 ADR-011）──长连接/轮询──▶ IM 平台（见 07）
```

### 4.1 插件宿主 ⇄ worker【建议，取自历史设计】

- 分帧：紧凑 UTF-8 JSON 加换行，单帧最多 8 MiB。
- 信封字段：`protocol`（固定 `"xtwork"`）、`version`、`kind`、`id`、`seq`、`sessionId`、`method`、`event`、`payload`、`error`、`meta`。`meta.sender` 取 `host`、`plugin:<id>` 等。
- 握手：worker 回复 `Role: "plugin"`，方法 `plugin.load`、`plugin.invoke`、`shutdown`，`Runtime: "xtwork/moejs"`（`cmd/xtwork-plugin/main.go:92`）。hello 超时 10 秒。
- 方法：
  - `plugin.load`（宿主 → 插件）：pluginId、api、entry、files、capabilities、tools、view、schedule，可选 timeZone。
  - `plugin.invoke`（宿主 → 插件）：kind（tool / view / schedule）、name、input、可选 context。output 最多 1 MiB。
  - `capability.call`（插件 → 宿主）：capability、method、位置参数数组 params（最多 1 MiB），结果 `{result}`。
  - `plugin.log` 事件：每分钟最多 60 条，每条最多 2,000 字符。
- **版本注意：** xtwork 协议 1.2 已冻结（2026-11-18），但 plugin 角色只在 1.3 里，1.3 尚未冻结。v2 参考 1.3 的帧格式，独立版本化。M2 结束时冻结已经验收的接口。

### 4.2 插件桥 ⇄ 插件宿主：v2 新增

xtwork 里插件宿主在 Go 主进程内，界面通过进程内的 `hostapi` 调用它，没有跨进程协议。v2 的插件宿主是服务端的子进程，必须新定义这一层。

- 格式：与 4.1 相同的信封与分帧，新增角色 `server`。
- 蓝本：`internal/hostapi/plugins.go`（92 行）的命令与 `PluginSnapshot`。
- 插件桥 → 插件宿主（草案）：
  - 管理：`plugins.snapshot`、`plugins.setEnabled`、`plugins.install`、`plugins.uninstall {deleteData}`、`plugins.reload`、`plugins.setFolder`。
  - 工具：`tools.list`（返回所有已启用插件的工具）、`tools.invoke {plugin, name, input, context}`。
  - 视图与上下文：`views.call`、`context.search`、`context.resolve`、`context.suggest`。
  - 事件：`events.publish`（对话事件，见 8.3）。
- 插件宿主 → 插件桥（草案）：`server.agent.*`、`server.notify`、`server.secrets.get`、`server.confirm.request`、`server.snapshotChanged`。
- `PluginSnapshot` 字段沿用：pluginId、name、version、description、icon、source、revision（SHA-256 前 16 位）、enabled、state（stopped / starting / running / failed）、capabilities、tools、views、error。

### 4.3 界面 ⇄ 插件桥

- 插件桥在服务端注册一个独立路由（例如 `/x/plugins`），复用服务端现有的环境鉴权。
- 不往 T3 的 contracts 里加 RPC 方法。理由：contracts 一个月有 472 个提交，加方法会让每次同步都可能冲突。只有“注册路由”一行属于补丁。

### 4.4 命名

【建议】worker 内部暂用 `"xtwork"` 作为协议标识、`xtwork` 作为能力对象。v2 在 M2 确定公开字段和契约版本。用户可见品牌由产品配置提供。

## 5. 插件清单（manifest）

### 5.1 v2 清单

`api: 2` 必须声明 `kind`。`functional` 允许 `worker`、功能 `capabilities`、`contributes.tools` 和 `contributes.views`。`appearance` 禁止这些字段，只允许静态 `contributes.theme`、受限图标和背景数据。两类清单不能混合，校验失败返回结构化诊断。

旧 `api: 1` 功能清单保留兼容读取路径。内置待办迁移到 v2 后，新的本地插件应直接使用 v2。

参考 xtwork 的 schema（`protocol/v1/plugin-manifest.schema.json`，`additionalProperties: false`；Go 侧校验 `internal/plugins/manifest.go`）。

| 字段 | 规则 |
|---|---|
| id | 2–32 字符，`^[a-z][a-z0-9]*(-[a-z0-9]+)*$` |
| name | 1–40 字符 |
| version | SemVer |
| api | 固定为 1（v2 的新增贡献点上线时升为 2） |
| description | 最多 200 字符 |
| icon | Pika 图标名 |
| worker | `.ts` 或 `.js`，不含 `.`、`..` 路径段 |
| capabilities | 从 storage、agent.tools、notify、schedule、usage.read、fs.folder 中去重选取（v2 新增项见第 6 节） |
| contributes.tools | 最多 16 个。字段 name（`^[a-z][a-z0-9]*(_[a-z0-9]+)*$`，≤32）、title、description（英文，≤1,024）、inputSchema（object，≤16 KiB）、可选 confirm。有工具就必须声明 agent.tools |
| contributes.views | 最多 4 个。字段 id、title、placement（panel / sidebar / settings）、entry（`ui/*.html`） |
| 目录限制 | 最多 512 个文件，合计 16 MiB，不允许符号链接 |

xtwork 的两个既有决定继续有效：
- 没有 `commands` 贡献点。
- 不设 `contributes.settings`：插件设置用 `placement: settings` 的视图提供。

v2 新增的贡献点（api 2）：

| 贡献点 | 内容 | 用途 |
|---|---|---|
| `contributes.contextKinds` | kind、label、是否出现在 @ 选择器 | 第 8.2 节的上下文条目 |
| `contributes.events` | 订阅的对话事件类型 | 第 8.3 节 |
| `contributes.tools[].surface` | `chip` 或省略 | 写入后在对话里显示确认条 |

> 注：远程连接（IM 接入）已按 [ADR-011](../decisions/011-mingle-im-bridge.md) 独立为 T3 监管的受信 Node 服务 `im-bridge/`，不再通过 `moejs` 插件清单的 `contributes.connectors` 或 `im-*` worker 承载，以保持 `moejs` 沙箱的零网络、零凭据边界。

## 6. 能力与权限

能力设计参考 xtwork 的决策 13 与权限说明：
- 宿主每次调用都检查清单和授权。内置插件可预授予普通存储能力，目录、外部连接和高影响动作走明确授权。
- Go 插件宿主负责能力裁决；插件只获得“manifest 与用户授权的交集”。
- 能力变化时重新确认：`SetPluginEnabled` 发现能力与当前授权不一致，返回 `capabilities_changed`。
- 插件默认没有网络能力。

xtwork 已有的能力与方法（`internal/pluginhost/capabilities.go:110-131`）：

| 能力 | 方法 | 限额 |
|---|---|---|
| `storage` | get、getMany、set、delete、list | 键 ≤200 字节、字符集 `[A-Za-z0-9._:/-]`；值 ≤256 KiB；每插件 16 MiB；list 最多 1,000 个键 |
| `fs.folder` | status、list、read、search、write | 文本 ≤256 KiB；write 只能在已确认的调用里使用，必须带 `expectedSha256`，冲突时返回 `{written:false, currentSha256}` |
| `schedule` | set、cancel、list | 插件自己的定时回调。最多 256 个；repeat 可选 daily、weekly、monthly；最近 7 天错过的补发一次 |
| `notify` | （通知） | title 1–100 字符，body ≤500 字符；每分钟 10 条 |
| `usage.read` | query | 最多 10,000 行 |
| `views` | notify | 通知插件视图刷新 |
| `agent.tools` | — | 不是调用接口，是“允许导出工具”的许可 |

v2 新增的能力【建议】：

| 能力 | 方法（草案） | 实现位置 | 使用者 |
|---|---|---|---|
| `agent.thread` | start、send、read、interrupt | 插件桥 → T3 对话服务 | 受信扩展（IM 桥走 T3 内部服务，见 [ADR-011](../decisions/011-mingle-im-bridge.md)） |
| `agent.request` | list、answer | 插件桥 → T3 待处理请求 | 受信扩展（IM 桥） |
| `agent.schedule` | create、delete（T3 定时任务） | 插件桥 → T3 定时任务服务 | calendar |
| `events` | 按类型订阅 | 插件桥 | 受信扩展 / 回合后建议 |
| `events.content` | 读取事件中的消息正文 | 插件桥 | 受信扩展 / 回合后建议 |
| `context` | 提供上下文条目 | 插件桥调用插件 | obsidian、todo、calendar |

命名说明：xtwork 的 `schedule` 指“插件自己的定时回调”（例如待办到期提醒）。T3 的“定时任务”是“到点让运行时执行一段提示”，v2 用 `agent.schedule` 表示，两者不混用。

敏感能力在启用时单独确认，并写清后果：
- `agent.thread`：插件可以替用户向助手发消息。
- `events.content`：插件可以读到对话正文。
- `fs.folder`：只限用户选定的目录。

宿主能力与 T3 内部服务的对应：
- `agent.thread.*` 对应 MCP 工具 `t3_thread_launch`、`t3_thread_send`、`t3_thread_read`、`t3_thread_interrupt` 背后的同一套服务。
- `agent.request.*` 对应 `t3_pending_request` 背后的待处理请求。
- `agent.schedule.*` 对应 `apps/server/src/scheduledTasks/ScheduledTaskService.ts`。时间类型：一次性（`runAt`）、间隔（`everyMs`，有最小值）、固定时刻（`timeOfDay` + 可选 `weekdays`）、webhook（`Schedule.ts`）。webhook 需要 T3 Connect 才有公网地址（`packages/contracts/src/orchestratorMcp.ts:755-757`：“Creation may omit it without T3 Connect remote access or run permission.”），v1 不用。

## 7. 界面槽位【建议】

| 槽位 | 内容 | 渲染方式 |
|---|---|---|
| 侧栏入口 | 待办、日程、笔记的图标与数量。放在侧栏底部原来 Pull requests、Issues 的位置 | 界面原生组件，数据来自插件 |
| 面板区 | `placement: panel` 与 `sidebar` 的插件视图 | 沙箱 iframe |
| 设置页 | “插件”分区：插件列表、状态、能力、启用开关；`placement: settings` 的视图；“远程连接”分区 | 列表原生，插件设置视图用 iframe |
| 输入框 @ 选择器 | 插件提供的上下文条目（笔记、待办、日程） | 界面原生 |
| 对话内确认条 | 写入类工具的结果，例如“已加入待办……［撤销］［打开］” | 界面原生，读取工具结果中的结构化数据 |
| 确认卡片 | `confirm: true` 工具的执行前确认 | 界面原生 |

xtwork 的视图实现依赖 mygo：`Window.NewWebView` + `PageOptions{Untrusted: true}`，每个页面独立临时 Session；地址 `xtplugin://<id>/`（Windows 上是 `http://<id>.xtplugin.localhost/`）；页面通过 `POST /__xtwork/call {method, params}` 调用，保留方法 `hello` 返回主题令牌、pluginId、viewId。

v2 的视图实现：
- 插件视图放进 T3 界面里的 iframe，`sandbox="allow-scripts"`（不含 `allow-same-origin`，因此是不透明源）。
- 视图文件由插件桥在**另一个本机端口**提供，与 T3 界面不同源。
- 响应头沿用 xtwork 的 CSP：`default-src 'none'; script-src <源>; style-src <源> 'unsafe-inline'; img-src <源> data:; font-src <源>; connect-src <源>; frame-src 'none'; object-src 'none'; base-uri 'none'`，加 `nosniff`。源必须显式写出协议与端口（xtwork 坑位 3）。
- 调用通道从 HTTP POST 换成 postMessage：宿主页面校验来源窗口和插件 id，再转给插件桥。iframe 只能调用自己插件的方法。
- 只改共享 kit（`plugins/builtin/kit/xtwork-view.js`，119 行）里的传输层。插件视图代码通过 kit 调用，不用改。`hello` 返回的主题令牌映射到 T3 的主题。
- xtwork testing.md 的要求在此成立：“如果支持不可信 UI，必须用独立 sandbox iframe 或 WebContents 与结构化 `postMessage` RPC。CSS scope 不能作为安全边界。”
- 【待验证 M2】WKWebView、WebView2、WebKitGTK 中，不透明源 iframe 加载另一端口的模块脚本、CSP、postMessage 的行为一致（xtwork 风险 R4：Untrusted WebView 只在 WKWebView 上验证过）。

可选路径：T3 已支持 MCP Apps，能在对话里内嵌渲染工具返回的界面（`packages/shared/src/mcpApp.ts`：协议版本 `2026-01-26`，MIME `text/html;profile=mcp-app`，扩展 `io.modelcontextprotocol/ui`，资源前缀 `ui://`，HTML 上限 5 MiB；组件 `apps/web/src/components/chat/McpAppFrame.tsx`）。目前看到工具界面元数据来自 Claude 适配器（`ClaudeAdapterV2.ts` 的 `tool_use_meta`），Pi 适配层的工具结果渲染需要单独验收。【待验证 M2】Pi 会话能否显示 MCP App。能的话，以后的富卡片可以走这个标准；v1 的确认条不依赖它。

## 8. 与 agent 的三种绑定

xtwork 里，插件与 agent 的绑定只有两种：工具（名字 `<id>__<name>`），以及输入框里的 `~` 引用（把运行中插件的贡献插入输入框）。没有插件向系统提示注入上下文的能力。v2 把绑定扩展为三种。

### 8.1 工具：agent 主动调用插件

- T3 MCP 工具名沿用 xtwork 规则：`<插件 id>__<工具名>`，插件 id 里的 `-` 换成 `_`，最长 64 字符（唯一实现 `hostapi.PluginToolName`）。例：`todo__create`、`calendar__list`、`obsidian__search`。Pi 会把 T3 MCP 工具加上 `mcp__t3-code__` 前缀，宿主继续使用原名。
- 注册：插件桥在 T3 的 MCP 服务里新增一个 `plugins` 工具集。现有工具集位于 `apps/server/src/mcp/toolkits/`：attachment、device、environment、html、issues、message、orchestrator、preview、previewControls、project、pullRequests、theme、thread、toolSearch、worktree。
- T3 把自己的 MCP 服务传给每个运行时会话，所以插件工具经 `provider-pi` 注入的 MCP 桥进入 Pi 会话，开发者功能下的其他运行时也可用。T3 没有“用户自配 MCP 服务”的设置（`packages/contracts/src/settings.ts` 中没有 mcpServers），插件工具只能经过这个工具集进入。
- 调用来源：MCP 请求带会话令牌，令牌对应一个对话（`apps/server/src/mcp/McpSessionRegistry.ts`）。插件桥把“哪个对话、哪个回合”放进 `plugin.invoke` 的 `context` 传给插件。待办据此记录来源，确认条据此显示在正确的对话里。
- 可见性：T3 对工具分级暴露，`McpToolExposure.ts` 的 `DIRECT_TOOLS` 只有 `orchestrator_capabilities`、`delegate_task`、`task_status`、`tool_search`，其余工具藏在 `tool_search` 后面。Pi 自带 `tool_search`，T3 的 Pi MCP 桥按运行时及模型协议激活工具。【待验证 M2】对默认模型验证自然语言待办发现，遇到实际漏工具时评估 P-09。
- 数量：xtwork 规定每个会话最多 128 个工具。v2 沿用。
- 返回值：给模型一段简短文字；给界面一份结构化数据（确认条与撤销用）。工具输出沿用 256 KiB 的编码上限。

**确认流程（`confirm: true` 的工具与 IM 作用域审批）：**
- xtwork：发出 `plugin.tool` 提示，只接受“允许一次”“本会话允许”“拒绝”，不接受工作区级授权；插件收到 `context.confirmed`；`fs.folder.write` 只能在已确认的调用里使用。
- v2：插件桥在执行前暂停这次工具调用，在桌面对话里显示确认卡片，用户决定后再执行；超时视为拒绝。对于由 IM 触发的混合回合，按 [ADR-011](../decisions/011-mingle-im-bridge.md) 首版统一回桌面原生审批，且强制采用绑定具体调用、参数与受众的**单次生效确认**（禁用“本会话允许”）；IM 平台内卡片审批留待 `Q-09` 真机验收后再按 Owner 身份核验开放。
- 【待验证 M2】T3 的 Pi 扩展在 Supervised 下会对写操作征求确认。验证插件自身的确认、拒绝与撤销，避免同一动作重复弹窗。

### 8.2 上下文条目：给 agent 附上资料

T3 的消息可以携带结构化上下文条目（composer context record）。已核实的规则：

| 规则 | 值 | 位置 |
|---|---|---|
| 内置类型 | image、file、terminal、element、preview-annotation、review-comment、mention、skill、thread、environment、response | `packages/contracts/src/composerContext.ts` |
| 自定义类型 | 不属于内置类型，且匹配 `^[a-z][a-z0-9-]{0,39}$` | 同文件 :38、:262 |
| 自定义条目内容 | `payload`：任意 JSON，序列化后 ≤64,000 字符 | 同文件，`UnknownContextRecord` |
| 条目 id | `^[a-z0-9_-]+$`，≤128 字符 | 同文件 |
| 每条消息 | 最多 200 个条目，id 不重复 | 同文件，`COMPOSER_CONTEXT_MAX_RECORDS` |
| 解码失败 | 丢弃该条目，不报错 | 同文件：“Undecodable records are dropped, not fatal.” |
| 发给运行时 | 自定义类型的 payload 经 `JSON.stringify` 放进 `<t3_context version="1">` 信封中的 `<context kind="…" id="…">` | `packages/shared/src/composerContextReferences.ts:394` 起 |

结论：**插件定义的上下文类型不需要改服务端，就能把内容送到运行时。**

约束：消息正文里必须出现指向条目的引用（输入框里的标签）。只有被引用的条目才会进信封。所以界面要做两件事（补丁 P-08）：
1. @ 选择器列出插件提供的条目；
2. 插件类型的条目在输入框里显示为可移除的标签。

xtwork 的 `~` 引用是这里的前身；v2 改用 T3 输入框的 @ 选择器，不再单独设 `~`。

流程：
1. 插件在清单里声明 `contextKinds`，例如 `obsidian-note`、`todo-item`、`calendar-event`。类型名以插件 id 开头，避免冲突。
2. 用户输入 @ 时，界面经插件桥调用插件的 `context.search(query)`，显示候选。
3. 用户选中后，界面调用 `context.resolve(id)` 取得 payload，插入标签与条目。
4. 可选：用户输入时，界面调用 `context.suggest(text)`，把候选显示为“可能相关”的标签（Obsidian 的规则见 [06 §4](06-内置插件-待办日程笔记.md#4-obsidian-笔记)）。

payload 写法约定（参照 T3 自己的 thread 条目：它在条目里写明用 `t3_thread_read` 读取全文）：
- 先放元信息：标题、路径或 id、更新时间。
- 再放内容：按预算截断，并标明 `truncated: true`。
- 最后放提示：需要更多时调用哪个工具，例如“需要全文时调用 obsidian__read”。
- 预算：单个条目默认 8,000 字符，一条消息里插件条目合计默认 24,000 字符【建议，M3 按实测调整】。

### 8.3 事件：插件观察对话

插件桥订阅 T3 编排事件，转换成一小组稳定的插件事件。插件通过 `contributes.events` 声明订阅，需要 `events` 能力；要读消息正文，还需要 `events.content`。

| 插件事件 | 含义 | 内容 |
|---|---|---|
| `thread.created` | 新对话 | 对话 id、标题、来源（界面 / 插件） |
| `message.user` | 用户发出消息 | 对话 id；正文需要 `events.content` |
| `turn.started`、`turn.completed` | 回合开始、结束 | 对话 id；结束时附最终回复（需要 `events.content`） |
| `request.pending`、`request.resolved` | 运行时请求权限、请求被处理 | 请求 id、类型、摘要、可选操作 |

只有插件桥依赖 T3 的事件结构。上游改事件，只改插件桥的映射。

用途：供未来功能插件做“回合后建议”（例如检查漏记的待办，只生成建议，不直接写入）。IM 远程连接的消息回复与首版桌面审批直接走 T3 服务端内的 IM 桥（见 [ADR-011](../decisions/011-mingle-im-bridge.md)），不经过 moejs 插件事件转发。

## 9. 存储

- 沿用 xtwork 的布局（数据根下）：

```
plugins/
├── registry.json
├── installed/<id>/            本地安装的插件；启动时清理 .staging-*
└── state/<id>/
    ├── data/                  storage 能力（键值）
    ├── schedules.json         schedule 能力
    ├── folder.json            fs.folder 选定的目录与目录身份
    └── log/                   插件日志，1 MiB 轮转
```

- v1 只提供键值存储，不加 SQLite。xtwork 的待办和日程各最多 1,000 条，键值存储够用。
- 内置插件用 `go:embed` 打进插件宿主；默认启用 todo、calendar，obsidian 默认停用（要先选 vault）。
- 卸载时询问是否删除数据（`UninstallPlugin {deleteData}`）。

## 10. 生命周期与限额（沿用 xtwork）

- 按需启动，空闲 5 分钟退出（IM 远程连接不在 moejs worker 内运行，而是由 T3 监管的独立 `im-bridge` 进程按绑定状态管理生命周期，见 [ADR-011](../decisions/011-mingle-im-bridge.md)）。
- 同一时间只处理一个调用，等待队列 32 个，溢出返回 `plugin_busy`。插件进程内并发的 `capability.call` 最多 32 个。
- 加载：只发送 `ui/` 以外的 .ts、.js、.mjs 文件，最多 256 个、合计 4 MiB；编译限时 5 秒，加载限时 5 秒。
- 期限：工具 30 秒；视图 10 秒；schedule 回调 30 秒；定时器回调 5 秒。定时器最多 64 个，最短间隔 10 毫秒。
- 崩溃：退避 1、2、4、8、16 秒；10 分钟内崩溃 5 次，标为 `failed`。
- moejs：`MemoryLimit` 64 MiB（近似值，坑位 5）；每次调用设 `Interrupt`；`CompileWith` 带 Context，因为 Interrupt 停不了编译（坑位 4）；`DisableDynamicCode` 为 true；不启用 node 与 webapi；只接受可擦除的 TS 语法。
- 进程环境：环境变量为空；工作目录是临时目录；时区用 IANA 名，配合 `time.LoadLocation` 和 `time/tzdata`。worker 不读写文件，不联网，源码由宿主在加载请求里发送。
- 错误码：`plugin_not_found`、`plugin_not_enabled`、`plugin_manifest_invalid`、`plugin_busy`、`plugin_timeout`、`plugin_failed`、`capability_denied`、`quota_exceeded`、`folder_not_selected`、`plugin_error`。
- v2 新增：`context.suggest` 期限 1 秒；`context.resolve` 期限 5 秒。

## 11. 安全

- 插件拿不到 T3 的 RPC 和 MCP 端点，只能使用被授予的能力。
- 插件视图在不透明源的 iframe 里运行，拿不到 `window.mygo`，也调不到服务端。
- 密钥只经过宿主，插件代码与视图都拿不到（IM 凭据见 [07](07-远程连接插件.md)）。
- 进程隔离和 moejs 能力限制用于内置插件。第三方插件公开分发前要验证操作系统级隔离边界，见 [11](11-风险与待定.md)。
- 审计：插件的每次写入类工具调用、每次 `agent.thread.*` 调用都记日志，包括插件 id、来源对话、时间。设置页可查。

## 12. 与 Pi 扩展的关系

- 产品插件由 Xtwork 的 Go 宿主和 moejs worker 管理。Pi 使用 T3 的运行时扩展接收已授权的 MCP 工具。
- 产品里只有一个“插件”概念，就是 moejs 插件。
- 内置 Pi 默认使用应用私有目录，加载应用指定的 T3 MCP 扩展。开发者自配的 Pi 实例可按其自身设置加载扩展。 [内置运行时](03-内置运行时-Pi.md)

## 13. 开发与调试

- 开发者功能打开后，可以安装本地插件；重载只在新版本校验通过后才替换旧版本（沿用 xtwork）。
- 设置页提供插件日志与最近调用记录。
- 插件工坊（AI 编写插件，`plugin_validate` 校验后启用）是 xtwork 已验收的流程。v2 要把它改成 T3 的项目加 MCP 工具，放到 v1 之后【待定 Q-10】。
