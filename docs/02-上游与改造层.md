## 1. 上游是什么

- 仓库为 [T3 Code](https://github.com/pingdotgg/t3code)，MIT 许可。
- 规划基线是 2026-11-18 的 [`3ce2145`](https://github.com/pingdotgg/t3code/commit/3ce2145864f1e8b822cc8dff9c8cfdf39d9e450b)。开工时重新选定一个提交，记录在 `upstream.lock`（规划中的文件）。
- 工程形态：pnpm monorepo。根目录 `packageManager` 为 `pnpm@12.14.0`，根 `engines.node` 为 `26.13.1`。
- 服务端可以脱离 Electron 运行：包名 `t3`，命令 `t3`（`dist/bin.mjs`），`engines.node` 为 `^22.16 || ^23.11 || >=24.10`（`apps/server/package.json`）。

| 目录 | 作用 | 产品是否使用 |
|---|---|---|
| `apps/server` | Node 服务端：编排、持久化、内置 MCP 服务、定时任务 | 使用 |
| `apps/web` | React 界面 | 使用 |
| `apps/desktop` | Electron 外壳 | 不使用。它的预加载脚本和桥接接口是我们外壳的参照（见 [04](04-mygo外壳.md)） |
| `apps/mobile` | React Native 客户端 | v1 不使用 |
| `packages/contracts` | 线协议，Effect Schema | 使用 |
| `packages/client-runtime`、`packages/shared` | 客户端运行时、共享逻辑 | 使用 |
| `packages/provider-*` | 各运行时的适配层（ACP、Claude、Pi 等） | 使用 ACP 适配层；其余只在开发者功能打开后可见 |
| `packages/source-control-*` | GitHub、GitLab 等代码托管 | 归入开发者功能 |
| `infra/relay` | T3 Connect 中继 | 不使用 |

规模（2026-11-18 实测，生产代码行数）：

| 部分 | 行数 |
|---|---|
| 服务端 `apps/server` | 311,413（另有测试 392,513） |
| 界面 `apps/web` | 约 336.6k |
| contracts + client-runtime + shared | 123,076 |
| desktop | 48,531 |
| mobile | 约 169k（TS） |
| 其中编排 orchestration-v2 | 109,585（`Orchestrator.ts` 16,565；`ClaudeAdapterV2.ts` 14,713） |

变动速度：2026-10-18 之后一个月共 6,144 个提交，约每天 200 个。按目录：服务端 2,483，界面 2,073，mobile 1,069，provider-* 618，client-runtime 551，contracts 472，desktop 313，source-control-* 253。

结论：上游体量大、变化快。我们只能“薄改”。改动越少，同步越便宜。

## 2. 改造层原则【建议】

1. **不做长期分叉开发。** 上游是只读输入。我们的全部改动放在改造层，构建时叠加到上游源码上。做法参考 VSCodium。
2. **改动只有四类：** 隐藏、改名、改默认值、加挂载点。不改上游的业务逻辑。
3. **能不打补丁就不打。** 手段优先级：
   1. 环境变量（例：关闭遥测）；
   2. 首次启动写入的设置（例：默认运行时）；
   3. 翻译覆盖（例：术语）；
   4. 新增包（例：插件桥）；
   5. 补丁（最后手段）。
4. **一个补丁只做一件事。** 每个补丁有编号、一句话目的、上游文件与行号锚点。
5. **记录合并成本。** 每次同步记一行：失败补丁数、改动行数、耗时。成本持续上升，就是重新审视改造范围的信号。

## 3. 代码仓库布局（规划，尚未创建）【建议】

```
xtwork_v2/
├── upstream/              上游源码，git submodule，锁定到 upstream.lock 的提交；不直接修改
├── overlay/
│   ├── brand/             品牌配置：名称、图标、bundle id、数据目录、URL scheme、支持链接
│   ├── patches/           对上游的补丁，按编号命名：P-04-developer-features.patch
│   ├── i18n/              翻译覆盖：zh.json、en.json 的术语改动
│   └── packages/          新增 TS 包：plugin-bridge（服务端）、plugin-slots（界面）、mygo-bridge（预加载脚本）
├── shell/                 mygo 外壳（Go）
├── plugin-host/           插件宿主（Go），按 v2 服务端边界实现
├── plugins/               内置插件：todo、calendar、obsidian、im-*
├── runtime/               Dim 版本锁、model.json 模板、prompts.base 覆盖文本及其上游 diff 记录
├── scripts/               apply-overlay、sync-upstream、rebrand、brand-check、build、release
└── docs/                  规划与设计文档（即本目录）
```

构建流程。`scripts/apply-overlay` 把 `upstream/` 复制到构建目录，依次应用补丁、执行改名脚本、覆盖翻译、链接新增包，然后按上游方式构建服务端和界面，最后由外壳打包。

## 5. 同步流程【建议】

1. 选定新的上游提交，更新 `upstream.lock`。
2. 运行 `scripts/sync-upstream`：拉取，依次应用补丁，报告失败的补丁。
3. 逐个修复失败的补丁，每个补丁单独提交。
4. 运行检查：类型检查；上游测试中与补丁相关的部分；品牌检查；启动冒烟（外壳启动 → 发一条消息 → 收到回复 → 退出后无残留进程）。
5. 在 `docs/同步日志.md`（规划中的文件）记一行：日期、上游提交、失败补丁数、改动行数、耗时。

节奏：两周一次【待定 Q-11】。上游的安全修复随时同步。

提前发现冲突：CI 每晚把补丁试应用到上游 main，只报告，不合并。

## 6. 不进产品的上游部分

- `apps/desktop`（Electron）：整体不用。
- `apps/mobile`：v1 不做。它依赖 T3 Connect 配对。
- `infra/relay`、T3 Connect、Clerk 登录：v1 关闭，见 [09](09-品牌与发布.md)。
- 浏览器预览：依赖 Chromium 调试协议（CDP）。
  - 桌面端：`apps/desktop/src/preview/Manager.ts:2807` 调 `debugger.sendCommand`；`DesktopBrowserHost.ts:327` 调 `Page.stopScreencast`。
  - 服务端：`apps/server/src/preview/ServerBrowserContexts.ts:188` 调 `chromium.launch`，`:306` 调 `connectOverCDP`。
  - WKWebView 没有 CDP。v1 把预览归入开发者功能，并标为“当前外壳不支持”。
