# 10 里程碑与验收

各阶段的实现进度与已跑过的测试见 [当前进度](../README.md#当前进度)。

【建议】先用一轮本机对话证明桌面壳和助手能配合，再做首页和插件。每个里程碑以可复现的用户操作验收。

## M0 · 跑通桌面、T3 和 Pi

1. 记录 T3、mygo、Node、Pi 的锁定版本，按 [04](04-mygo外壳.md) 启动。
2. 在 macOS arm64 上启动 T3 Node 服务端，mygo WebView 加载本机界面。先验证浏览器模式，再验证生产构建的同源页面、preload 和最小桌面桥接。
3. 用随包 Pi 启动原生 RPC。验证模型发现、首字流式输出、待办 MCP、取消、权限拒绝、自我介绍以及重启后原线程续聊，记录命令、版本和结果。
4. 关闭窗口、重新打开、彻底退出。核对何时保留后台进程。确认显式退出后，这次启动的服务端、Pi RPC 进程、插件宿主和 worker 都已退出。

**通过条件**　新数据目录能首启、收到流式回复、创建待办并在重启后读回。检查一份旧 Alpha 数据的默认设置迁移、对话和待办。Windows 启动信息和子进程管理的验证可以独立进行。

## M2 · 插件通路

- Go 插件宿主带一个测试 worker，接通 JSONL 加载、工具调用、授权和停止。
- 插件桥把一个工具接进 Pi 的会话 MCP，并返回插件写入结果。在界面只展示实际已执行的操作。
- 接通一个 @ 上下文条目和一个沙箱面板。核对手工选择、移除、权限拒绝、退出后恢复。
- 核对 MCP 工具是否需要特别暴露、权限是否重复弹窗。用一条测试流程打通确认、拒绝和撤销。
- 冻结这一阶段实际用到的 v2 插件契约和最小夹具。
- 第一阶段已合入 `main`（[PR #11](https://github.com/oulkurt/Xtwork-v2/pull/11)–[PR #13](https://github.com/oulkurt/Xtwork-v2/pull/13)）：补齐 v2 清单强判别、功能与外观双轨注册、结构化诊断，以及基于 `AppRouteModal` 的 `PluginModalHost`；待办操作回执、撤销与 `@` 上下文已于 [PR #10](https://github.com/oulkurt/Xtwork-v2/pull/10) 合入。

**通过条件**　同一测试插件能经对话和面板访问同一份状态。重复发送或重试只写一次，禁用插件后新工具调用无法执行。

## M6 · 跨设备互联与多机流转（独立演进线，【已定】见 [ADR-015](../decisions/015-cross-device-interconnect-and-e2e-relay.md)）

面向任意外部用户交付，不绑定自有企业微信、不依赖官方 T3 Connect / Clerk；当前暂不排期开工，后续严格按风险门禁分五阶段推进（详规与验收矩阵见 [14 跨设备互联与多机流转](14-跨设备互联与多机流转.md)）：

- **M6.0 · Gate 0（传输能力矩阵与协议冻结）**：冻结 10 项传输能力验收矩阵、`xtwork-relay/v1` 二进制分块/质询注册/握手向量（含可选 `M6.2a` 过渡模式与 `M6.2b` 盲转 E2EE 升级兼容约定）、客户端 Loopback Gateway 与服务端进程内 `PeerLinks` 双接入缝以及 mygo 更新管道跨平台契约。
- **M6.1 · 直连 / Tailscale / SSH 闭环 + 远端模拟器 + 桌面跨机委派**：零云端依赖、无需自研 E2EE，在 mygo 壳补齐 LAN 暴露、Tailscale Serve 与 SSH 隧道，上线 Xtwork 精简「跨设备互联」卡片并放开 `DevicePanel`；真机验收两机线程互控、远端 Mac iOS 模拟器交互、桌面 `local_only` 跨机 `PeerLinks` 委派与取消恢复（IM/群聊继续硬禁）。
- **M6.2 · 零账号公网中继（`xtwork-relay/v1`）+ Loopback Gateway + 自托管（渐进 E2EE）**：交付单二进制 Go 中继服务 + CF Workers DO（自定义域名）双服务端、Host Ed25519 质询注册（防 `4000` 抢占）、一次性二维码/URI 配对、单设备独立撤销、50 MiB 分块上传与 AVCC/MJPEG 实时流式背压；允许先以可选 `M6.2a`（TLS + Host 质询 + T3 鉴权最小中继）快速跑通公网链路，再沿同套二进制分块与 Loopback Gateway 缝隙平滑升级至 `M6.2b` 完整盲转 E2EE（上线面向外部用户的托管公网节点前须补齐或明示安全边界）。
- **M6.3 · mygo 壳远程两阶段更新 + 跨平台补齐**：在 `shell/` 补齐 `desktopTelemetryFd` / `desktopTelemetryControlFd`（POSIX `ExtraFiles` fd 4/5 与 Windows 等价本地 IPC），打通 `environment:maintain` 鉴权下的 prepare → confirm → commit 两阶段远程桌面更新；按 `Q-12` / `Q-15` 评估 Linux（含 Omarchy）控制端或无头服务端形态。
- **M6.4 · 可插拔身份控制面 + 机器共享与远期 P2P 评估**：抽象 `IdentityAdapter`（默认仍可零账号使用；支持 Passkey / 通用 OIDC / 企业微信 OIDC 平级可插拔以提供多设备自动发现），借鉴 Lody 引入按项目机器共享策略、`generation` 隔离与签名执行意图信封；实测后再决定是否引入 `iroh` / QUIC 打洞作为可选加速路由。

**通过条件**　未开启跨设备暴露时本机保持仅 `127.0.0.1` 监听且零新增外网连接；开启后可在零账号下通过直连或公网中继完成跨机线程控制、远端 Mac iOS 模拟器交互、50 MiB 附件上传、桌面 `local_only` 跨机委派与单设备即时撤销，远程更新完整执行两阶段确认且不绕过既有 IM/群聊硬拒绝边界。

## 依赖关系

`M0 → M1 → M3` 与 `M0 → M2 → M3`。M2 可以在 M1 打磨界面时并行。M4 依赖 M2，经批准的远程功能不妨碍 M3 成为桌面预览版。M5 按本次发布范围核对已完成的里程碑。**M6（跨设备互联）为独立演进线**，M6.0–M6.2 依赖 M1 桌面底座稳定，M6.3 远程更新依赖 M5 正式签名发布源；M6 整体不阻塞 M1–M5 首发交付。
