# 01 架构

> 回答：产品由哪些进程组成，各自负责什么，数据怎样流动，依赖朝哪个方向。
> 相关：[02 上游与改造层](02-上游与改造层.md) · [03 内置运行时](03-内置运行时-Pi.md) · [04 mygo 外壳](04-mygo外壳.md) · [05 插件系统](05-插件系统.md)

## 1. 分层

| 层 | 技术 | 来源 | 职责 |
|---|---|---|---|
| 外壳 | mygo（Go） | 新写 | 窗口、系统集成、启动并监管服务端、桌面桥接 |
| 界面 | React | 上游 apps/web + 改造层 | 对话、设置、插件槽位 |
| 服务端 | Node（Effect） | 上游 apps/server + 改造层 | 编排、持久化、内置 MCP 服务、定时任务、插件桥 |
| 运行时 | Pi（内置助手「小瞳」）+ 外部编码 Agent（原生 Claude/Codex、ACP Registry、本地 ACP） | 随应用打包 Pi，复用 T3 原生 `provider-pi`、`ClaudeDriver`、`CodexDriver` 与 `AcpRegistryDriver`（见 [ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md)） | 执行对话、调用模型和工具、保存原生会话；并支持通过 T3 `delegate_task` 将编码任务委派至选定 Coding Agent |
| 插件宿主 | Go | 来自 xtwork | 插件注册、安装、授权、存储、监管 moejs worker |
| 插件 | moejs（TS/JS 沙箱） | 新写（部分来自 xtwork） | 待办、日程、笔记的业务逻辑 |
| IM 远程连接服务 | Node（复用 Mingle MIT 渠道层） | 独立子包 `im-bridge/`（见 [ADR-011](../decisions/011-mingle-im-bridge.md)） | 飞书/微信/企微长连接与长轮询、扫码绑定、系统钥匙串、群背景缓存与消息归一化 |

## 2. 进程树

```
外壳（mygo，Go）
├─ 窗口：系统 WebView 加载 http://127.0.0.1:<端口>/（T3 界面）
│   ├─ PreloadScript 注入 window.desktopBridge → 调用外壳的 Go 服务
│   └─ 插件界面：沙箱 iframe（不透明源）
├─ 托盘、菜单、通知、更新
└─ 服务端（T3，Node）                        外壳启动并监管
    ├─ 编排 orchestration-v2、持久化、定时任务、伴侣记忆（ROLE.md / MEMORY.md / notes/）
    ├─ 内置 MCP 服务 /mcp                    运行时经它调用工具（按会话令牌鉴权）
    ├─ 插件桥与 IM 桥（新增，TS）
    ├─ 运行时：Pi --mode rpc                 T3 按会话启动，走 stdio JSONL
    ├─ IM 远程连接服务（im-bridge，Node）     T3 监管，绑定平台后启动长连接/轮询（飞书 / 微信 iLink / 企微）
    └─ 插件宿主（Go）                         插件桥启动并监管
        ├─ todo worker（moejs 进程）
        ├─ calendar worker（moejs 进程）
        └─ obsidian worker（moejs 进程）
```

产品提供模型服务与自带 Key / OAuth 订阅渠道均纳入内置助手「小瞳」的模型平面，通过本机保协议凭据隔离网关（OS 钥匙串托管公司长效 Key、19 类供应商 Key 与 OAuth Refresh Token）供给随包 Pi；外部编码 Agent（Claude Code、Codex、Kimi Code、Qoder、Codebuddy Code、DeepSeek Harness）运行在独立的运行时平面。见 [13 模型网关](13-模型网关.md) 与 [ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md)。

## 3. 依赖方向

```
插件（moejs） ◀──插件协议──▶ Go 插件宿主 ◀──JSONL──▶ T3 插件桥
运行时（Pi） ◀──Pi RPC──▶ T3 服务端（编排）
运行时（Pi） ──HTTP MCP──▶ T3 服务端（插件工具）
界面 ──T3 RPC / WebSocket──▶ T3 服务端
界面 ──postMessage──▶ 插件 iframe（只经宿主页面中转）
外壳 ──启动契约（--bootstrap-fd 0）──▶ T3 服务端
界面 ──DesktopBridge──▶ 外壳
```

规则：
1. 插件只认识插件协议。运行时使用 T3 MCP 发现和调用插件工具，插件宿主集中管理授权和存储。
2. 插件宿主只认识插件协议和插件桥提供的“宿主能力”。
3. 只有插件桥依赖 T3 内部服务。上游变动造成的适配工作集中在插件桥这一处。
4. 外壳只依赖两样东西：服务端的启动契约和 `DesktopBridge` 接口。
5. T3 原生适配层通过 Pi RPC 管理会话和回合，通过会话级 MCP 接入插件。

## 4. 为什么插件宿主挂在服务端下，而不是外壳下

- 服务端是 agent 世界的中心：对话、工具（MCP）、事件、持久化都在这里。插件要做的事几乎都要经过它。
- 服务端可以脱离外壳运行。插件跟着服务端走，以后服务端跑在远程机器上，插件和远程连接照样工作。
- 外壳保持薄：只管窗口和系统。外壳的问题不会拖垮插件，插件的问题也不会拖垮窗口。

## 5. 关键数据流

### 5.1 聊天中提到待办

1. 用户在输入框写：“周五前把季度报告发给王总。”
2. 服务端把消息交给运行时。
3. 运行时根据系统提示中的插件规则，调用 MCP 工具 `todo__create({title: "把季度报告发给王总", due: "2026-11-20"})`（以 2026-11-19 发出消息为例）。
4. 服务端 MCP 服务把调用交给插件桥 → 插件宿主 → todo worker。worker 写入存储，返回新条目。
5. 插件桥发出事件，界面在对话里显示确认条：“已加入待办：把季度报告发给王总 · 周五”［撤销］［打开］。
6. 运行时继续回复用户。

### 5.2 引用 Obsidian 笔记

1. 用户在输入框输入 @，从笔记选择器里选一篇笔记；或者界面根据输入内容建议几篇相关笔记，以可移除的标签显示。
2. 界面给消息附上一个上下文条目：`kind: "obsidian-note"`，`payload: {path, title, content, truncated}`。
3. 服务端把未知类型的条目原样转成 JSON，放进发给运行时的 `<t3_context version="1">` 信封（`packages/shared/src/composerContextReferences.ts:394` 的 `projectComposerContextForProvider`）。**服务端不用改。**
4. 运行时读到笔记内容。需要更多内容时，再调用 `obsidian__read` 工具。

### 5.3 从飞书/微信/企微发起任务【已定，见 ADR-011】

1. 用户在 IM 私聊或已放行群聊中 `@机器人` 发消息（群内未 `@` 的闲聊只存入 `im-bridge` 背景缓存，不进入桌面侧栏）。
2. T3 监管的 `im-bridge`（复用 Mingle MIT 渠道层）通过长连接/长轮询收到事件，经去重与门禁（`access.ts`）后以不可信数据信封推送给 T3 IM 桥。
3. T3 IM 桥按私聊/回复链/飞书话题路由到已有 Thread 或新建一条免项目工作区 Thread，在桌面侧栏展示该任务，并交由内置 Pi（或开发者模式下的其他 Provider）处理。
4. 若任务涉及本机 Shell、工作区外文件、跨聊天外发或高危插件写入，T3 挂起为 `request.pending`，仅允许 Owner 批准（先走桌面原生确认，后续按 `Q-09` 开放带 Owner 身份核验的 IM 卡片审批）。
5. 进度与最终结果由 `im-bridge` 按各平台原生方式（飞书流式卡片、企微流式回复、微信分段文本）发回来源聊天。

平台接入与安全细节见 [07](07-远程连接插件.md) 与 [ADR-011](../decisions/011-mingle-im-bridge.md)；将远程连接统一归属到 Captain 式 `Leader` 主管、侧栏顶部固定入口与按 run fail-closed 策略的设计见 [ADR-013](../decisions/013-leader-supervisory-threads.md)（Slice 1 / Slice 2 已于 [PR #25](https://github.com/oulkurt/Xtwork-v2/pull/25)、[PR #31](https://github.com/oulkurt/Xtwork-v2/pull/31) 合入 `main`）。

## 6. 数据目录【建议】

```
<数据目录>/                 名称随品牌定【待定 Q-01】；不使用 ~/.t3
├── userdata/              T3 服务端状态（数据库、附件）
├── scratch/               免项目对话的工作目录
├── runtime/
│   └── pi/                Pi 私有 agent 目录、动态生成的 models.json 与原生 sessions/
├── channels/
│   └── channels.json      小瞳模型渠道元数据（不含明文凭据，密钥均在 OS 钥匙串 app.xtwork.model-channels）
├── tools/                 由 Xtwork 一键安装的受管外部编码 Agent 目录（如 codex / deepseek-harness / ACP 缓存）
├── im/                    im-bridge 数据（im.db 去重/游标/绑定/已放行群 FTS5 背景、隔离 workspaces/ 与日志）
├── companion/             伴侣记忆（PR #25 已幂等迁至 companion/leaders/<leaderId>/{ROLE.md,private/,groups/<chatKey>/}）
├── workspace/             桌面服务默认工作目录，跨版本稳定
├── plugins/
│   ├── registry.json      插件宿主的注册表与授权记录
│   └── state/<插件 id>/   每个插件独立的状态目录
└── logs/                  外壳、服务端、插件宿主的日志
```

模型 API Key、OAuth 凭据与 IM 应用凭据均由单一硬化共享 OS SecretStore（`im-bridge/src/platform/secrets.ts` + `runtime/secretStore.ts`，命名空间分别为 `app.xtwork.model-channels` 与 `app.xtwork.im-bridge`）保存，零明文文件回退。T3 原有服务端凭据存储独立，见 [13](13-模型网关.md)。

## 7. 生命周期

启动：
1. 外壳取得单实例锁，选端口。
2. 外壳启动服务端，经启动 stdin 传入配置；等待健康检查通过。
3. 外壳建窗口，加载界面。
4. 服务端启动插件桥与 IM 桥；插件桥启动插件宿主并按需启动 moejs worker；IM 桥使用随包 Node 启动 `im-bridge` 完成握手，仅在存在已绑定平台或处于临时配对态时建立外网连接。
5. 用户发第一条消息时，T3 的 Pi 适配层启动 RPC 会话进程。

退出：
1. 用户从托盘选“退出”，或系统关机。
2. 外壳在 `App.OnBeforeQuit` 中请求服务端优雅关闭。
3. 服务端关闭运行时会话、优雅关闭 `im-bridge`（断开 IM 长连接并刷盘状态）、关闭 Go 插件宿主（先停 moejs worker）。
4. 超时后，外壳只结束自己记录过 PID 的进程。
5. 验收：退出后没有残留进程（服务端、Pi RPC 子进程、`im-bridge`、插件宿主、worker）。

## 8. 与 xtwork 架构的差异

| 方面 | xtwork | v2 |
|---|---|---|
| 界面 | mygo 原生界面（3E 系列切片） | T3 的 React 界面 |
| 运行时 | Pi sidecar | 随包 Pi CLI，使用 T3 原生适配 |
| 对话与持久化 | 自建 session log、timeline | T3 的编排与持久化 |
| 插件宿主位置 | mygo 宿主进程内 | T3 服务端的子进程 |
| 插件 | moejs，使用过未冻结的 1.3 插件角色 | moejs，v2 自己锁定插件契约（见 [05](05-插件系统.md)） |

迁移细节见 [12](12-从xtwork迁移.md)。
