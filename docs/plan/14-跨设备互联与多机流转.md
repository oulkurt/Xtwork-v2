# 14 跨设备互联与多机流转

> 【已定 · 架构与分阶段顺序】按 [ADR-015](../decisions/015-cross-device-interconnect-and-e2e-relay.md) 执行（2026-11-26 架构定稿，2026-11-27 补充渐进式 E2EE 口径）。作为独立演进线 **M6** 推进，**暂不排期开工，不阻塞 M1–M5 桌面与 IM 首发验收**。
>
> **边界区分**：[07 远程连接插件](07-远程连接插件.md) 解决的是**「人在手机/IM（飞书、微信、企微）里给单机小瞳派活」**；本篇解决的是**「电脑 A 的小瞳 Work 直接控制电脑 B（如公司 Mac）上的对话、查看并操控远端 iOS 模拟器、跨机委派不同智能体以及远程更新远端桌面版」**，且面向任意外部用户交付，**不绑定企业微信，也不依赖官方 T3 Connect / Clerk**。
>
> **E2EE 渐进落地口径（2026-11-27 确认）**：盲转 E2EE 是中继阶段的明确目标方向，但**不作为首期阻塞前提**——M6.1 先以 LAN / Tailscale / SSH 直连闭环（复用 WireGuard / SSH / TLS 加密），M6.2 公网中继允许按需分 **M6.2a（传输层 TLS + Host 质询 + T3 鉴权的最小自托管中继，UI 诚实明示非盲转 E2EE）→ M6.2b（X25519 + Ed25519 + AEAD 完整盲转 E2EE）** 平滑升级，协议帧头与路由层一次设计到位、零返工。

相关章节见 [01 架构](01-架构.md)、[02 上游与改造层](02-上游与改造层.md)、[04 mygo 外壳](04-mygo外壳.md)、[07 远程连接插件](07-远程连接插件.md)、[09 品牌与发布](09-品牌与发布.md)、[10 里程碑与验收](10-里程碑与验收.md) 与 [ADR-015](../decisions/015-cross-device-interconnect-and-e2e-relay.md)。

## 1. 目标场景与能力定位

| 目标能力 | 承载层 | 默认是否需要账号 / 企微 | 传输依赖 |
|---|---|---|---|
| **同机多智能体流转**（切换与委派） | 已于 M1c 实建（[ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md)） | 不需要 | 本机 |
| **跨设备控制远端机器 Thread** | T3 原生多环境 WS/HTTP + `connection-catalog` | **不需要**（零账号配对码即可用） | Direct/LAN → Tailscale/SSH → 中继（目标盲转 E2EE，首期允许 TLS 最小中继过渡） |
| **查看并交互远端 Mac 的 iOS 模拟器** | T3 原生 `DeviceService` + `DeviceHubProxy` + `DevicePanel` | **不需要** | 直连/Tailscale 优先 WebRTC；中继走 AVCC（需本机 Secure Context）/ MJPEG + 输入 WS |
| **跨设备智能体互调（Agent → 远端 Agent）** | T3 原生 `PeerLinks` + `PeerForwarding`（`/mcp`）+ 签名意图信封 | **不需要**（首期仅限桌面 `local_only`，IM/群聊继续硬禁） | 直连/Tailscale HTTPS 或服务端进程内 Relay Transport |
| **从一台电脑远程更新另一台电脑的小瞳 Work** | T3 原生 `ServerSelfUpdate` / `DesktopAppUpdate` + mygo 控制管道 | **不需要**（需 `environment:maintain` 权限与显式确认） | 已连接的任一远端环境路由 |
| **多设备自动发现与按项目机器共享** | 可选 `IdentityAdapter`（Passkey / 通用 OIDC / 企业微信 OIDC 平级） | **按需可选**（不启用时保持零账号） | 控制面仅管发现与撤销，不进入正文流量热路径 |

## 2. 总体分层与双接入缝设计

```text
控制端（如家里电脑 / 笔记本 / Linux）                      被控端（如公司 Mac）
┌─────────────────────────────────────┐               ┌─────────────────────────────────────┐
│ T3 Web 界面 / DevicePanel           │               │ T3 服务端（唯一权威状态机）           │
│  ├─ 直连/Tailscale → 直接 HTTP/WS   │               │  ├─ 线程 / 文件 / EnvironmentAuth    │
│  └─ 中继路线 → 127.0.0.1 Loopback   │               │  ├─ /mcp（PeerLinks / ModeLimit）   │
│      Gateway（Secure Context，WebCodecs）           │  ├─ /api/device-hub（iOS 模拟器流）  │
│                                     │               │  └─ DesktopAppUpdate（两阶段更新）   │
│ 本机 T3 服务端 PeerLinks            │               │          ▲                           │
│  └─ 逻辑地址 xtwork-relay://...     │               │          │ fd 4/5 (POSIX) / IPC (Win)│
│      → 进程内 Relay Transport       │               │ mygo 外壳（mygo.Updater + 暴露控制） │
└──────────────┬──────────────────────┘               └──────────▲──────────────────────────┘
               │                                                 │
               │ 1. Direct / LAN / Tailscale / SSH（优先 500ms 竞速）
               │ 2. Relay（xtwork-relay/v1：M6.2a TLS 过渡 / M6.2b 盲转 E2EE）
               ▼                                                 │
      ┌──────────────────────────────────────────────────────────┘
      │  中继服务（可选：用户自托管 Go 单文件 / CF Worker 自定义域名 / 官方大陆节点）
      └──────────────────────────────────────────────────────────
```

### 关键架构缝隙（开工前已锁定）

1. **客户端 UI 与 `PeerLinks` 必须分缝接入**：
   - **客户端 UI（`apps/web`）**通过 mygo/本机进程提供的按环境隔离的 `127.0.0.1:<port>` Loopback Gateway 接入上游 `ConnectionResolver` 与 `ConnectionDriver.connectOverRoutes`。因为 `127.0.0.1` 是浏览器原生 Secure Context，WebCodecs 解码 iOS AVCC 视频流无需 HTTPS 自签证书即可直通。
   - **服务端 `PeerLinks`（`apps/server/src/peer/PeerLinks.ts`）** 原生拒绝 `isOwnLoopback` 地址以防止本机冒充与端口漂移。因此服务端跨机 `/mcp` 严禁持久化 `127.0.0.1:<port>`，必须持久化逻辑路由 `xtwork-relay://<relayHost>/<roomId>` 及已钉选的 `hostPubKey` 与 `expectedEnvironmentId`，通过服务端进程内 Relay Transport 建连。
2. **与 `codingAgent` 设置的交互边界**：
   - 当本机桌面设置了 `codingAgent.mode === "provider"`（锁定本地某个外部编码 Agent）时，保持 [ADR-012](../decisions/012-xiaotong-model-channels-and-coding-agents.md) 与 `codingAgentDelegation.ts` 的既有规则，阻止小瞳隐式把本地编码任务改派给远端机器；
   - 当 `codingAgent.mode === "auto"` 或用户在桌面显式发起跨机任务（如 `t3_environment_links` / `t3_thread_launch(environmentId)` / 指定远端 `delegate_task`）时，允许桌面 `local_only` 线程经 `PeerLinks` 委派至远端；
   - 所有 IM 来源与 `group` 受众线程（含派生子线程祖先链）继续**无条件硬拒绝**跨机外部委派。

## 3. `xtwork-relay/v1` 中继协议与安全精化【建议 · M6.0 冻结】

参考 [`nanami-0713/relay-kit`](https://github.com/nanami-0713/relay-kit)（MIT）的中继拓扑与 [`LodyAI/Lody`](https://github.com/LodyAI/Lody)（Apache-2.0）的设备信任模型，但修复了两者直接套入 T3 时的全部硬伤，并支持 M6.2a（TLS 过渡）向 M6.2b（盲转 E2EE）平滑演进：

| 设计点 | `relay-kit` 原版行为 | `xtwork-relay/v1` 精化方案 |
|---|---|---|
| **宿主房间注册** | 知道 `tokenHash` 即可注册，新连接 `4000` 踢掉旧连接 | 被控端持有硬化 OS SecretStore（`app.xtwork.cross-device`）中的 **Host Ed25519 密钥对**；房间 ID 由 `hostPubKey` 派生；注册 `/agent` 须对中继下发随机 nonce 完成 Ed25519 质询签名，杜绝泄露路由引发的宿主抢占 DoS |
| **配对、加密与长期授权** | 单一 256-bit `code` 即全部权限；自制未审计 PAKE | 配对二维码/URI 仅作**一次性短期 bootstrap（10 分钟过期、用后即废）**，携带 `{ relayUrl, roomId, hostPubKey, pairingSecret(128-bit), t3PairingCode, expiresAt }`；帧头携带 `encryptionMode` 协商位：**M6.2a 可选过渡**走 `wss://` TLS + Host 质询 + T3 原生鉴权（UI 显式提示非盲转 E2EE）；**M6.2b 目标态**升级为标准 **X25519 临时 ECDH + Ed25519 双向 transcript 认证 + AEAD（AES-256-GCM / XChaCha20-Poly1305）+ 严格递增 counter 防重放**；均换取该控制端专属 `clientPubKey` 绑定的 T3 Session |
| **设备吊销** | 泄露 `code` 只能重换码，影响全部设备 | 每台控制端拥有独立 `clientPubKey` 与 T3 Session（区分 `read` / `operate` / `maintain` scope）；在被控端点击撤销某设备，立即关闭其中继隧道并吊销 T3 Session，其他设备不受影响 |
| **帧编码与上传上限** | JSON 包装 + 双重 Base64（+78% 膨胀）；请求体单帧不分块 | **纯二进制长度前缀帧**（消除双重 Base64）；请求方向支持 `hbegin` / `hchunk` / `hend` / `hcancel` 流式分块，完整支持 T3 50 MiB 文件与 10 MiB 图片上传 |
| **长流与背压** | E2E 模式无发送背压；`TunnelResponse` 全量缓存响应体 | 端到端发送/接收窗口背压；控制端 Loopback Gateway 收到 `hres`/`hchunk` 立即边收边写 HTTP 响应流，支撑无限 AVCC / MJPEG 视频流与 SSE |
| **服务端与大陆可达性** | 默认 CF `*.workers.dev`（大陆阻断） | 同协议双实现：① **单二进制 Go 中继服务**（默认官方大陆可达节点 + 用户/企业内网自托管首选）；② **Cloudflare Workers DO（Hibernation API，须绑自定义域名）**；中继内置连接数/单房间带宽/帧率限流防护 |

## 4. 五阶段推进顺序与门禁矩阵（M6.0 → M6.4）

严格坚持**先直连闭环 → 再零账号公网中继（支持 TLS 过渡到盲转 E2EE）→ 再远程更新与多端 → 最后可选身份控制面**的顺序，每个阶段必须通过退出门禁才能进入下一阶段。

### M6.0 · Gate 0：传输能力矩阵与协议冻结

- **目标**：在写产品功能代码前，把跨设备传输、双接入缝、密码学握手（含渐进加密协商位）与远程更新管道全部定为可测试契约。
- **前置条件**：[ADR-015](../decisions/015-cross-device-interconnect-and-e2e-relay.md) 生效。
- **交付物**：
  1. 冻结 **10 项传输能力验收矩阵**：普通 GET/POST、OAuth 配对与 Bearer/DPoP 换取、标准 `/ws` RPC、`/mcp`、`DeviceHubProxy` AVCC 长流、MJPEG 长流、设备输入 WS、50 MiB 文件分块上传、`ServerSelfUpdate` 两阶段 prepare/commit、断线重连与取消传播；
  2. 冻结 `xtwork-relay/v1` 二进制帧格式、Ed25519 质询注册、`encryptionMode` 协商位、X25519+Ed25519 握手测试向量与错误码表；
  3. 明确 mygo 壳 `DesktopTelemetry` 双管道在 POSIX（fd 4/5）与 Windows（本地 IPC）下的对齐方式；
  4. 核对并记录 `overlay/patches/` 新增补丁预算，确保不侵入 T3 上游核心编排逻辑。
- **退出门禁**：协议规范与测试夹具（含离线加密向量与模拟坏包/重放/抢占用例）通过评审；不修改默认产品行为。
- **明确不做**：不上线 UI 入口、不部署线上中继、不触碰 M1–M5 现有代码。

### M6.1 · 直连 / Tailscale / SSH 闭环 + 远端模拟器 + 桌面跨机委派

- **目标**：在**零云端服务依赖、无需自研 E2EE** 下，先在真实两台机器（局域网 / Tailscale / SSH）上跑通 T3 原生跨设备能力与 mygo 壳闭环。
- **前置条件**：M6.0 通过。
- **代码边界**：
  - **`shell/`（mygo 外壳）**：在 `shell/backend.go`、`shell/bridge.go` 与 `shell/preload.js` 补齐受控网络暴露（默认仍为 `local-only`；用户显式开启后支持局域网 `0.0.0.0` 绑定与 Tailscale Serve HTTPS）、`getAdvertisedEndpoints` 以及 `SSH` 隧道生命周期管理（含密码/私钥提示桥接与退出清理）。
  - **前端（`overlay/files/` + 最小 `overlay/patches/`）**：不直接放开含 Clerk/T3 Connect 的上游连接页，新增 Xtwork 精简「跨设备互联」设置卡片（复用 `connection-catalog`，提供：开启本机允许被连、生成配对码、添加远端直连/Tailscale/SSH 机器、查看与撤销已连客户端）；在跨设备互联或开发者功能启用时放开 `DevicePanel` 与受控 `/settings/devices`。
  - **服务端（`overlay/files/apps/server/src/`）**：放开 `linkedEnvironmentsEnabled` 受控开关，确认桌面 `local_only` 线程可通过 `PeerLinks` 委派至远端并保留 `T3-Mode-Limit` 与 `linkOrigin`；保留 IM/群聊与本地锁定 `codingAgent` 的既有限制。
- **退出门禁（真机两机实测）**：
  1. 机器 A 经 LAN、Tailscale 与 SSH 三种路径分别添加并控制机器 B（Mac）上的对话，断网重连与状态同步无丢消息；
  2. 机器 A 在右侧 `DevicePanel` 打开机器 B 上的 iOS 模拟器，实时画面（WebRTC / AVCC）与点击/输入交互正常，撤销机器 A 会话后画面流与输入 WS 立即断开；
  3. 机器 A 的桌面 `local_only` 对话经 `PeerLinks` 向机器 B 委派任务并支持等待、读取、父停止递归取消与重启恢复；IM/群聊线程尝试触发跨机委派 100% 返回 `delegation_denied_in_im`；
  4. 未启用跨设备暴露时，冷启动与空闲态仍仅监听 `127.0.0.1`，零新增外网流量。
- **明确不做**：不引入公网中继、不做账号系统、不做远程桌面更新。

### M6.2 · 零账号公网中继（`xtwork-relay/v1`）+ 本机 Loopback Gateway + 自托管（渐进 E2EE）

- **目标**：把跨设备能力从“同内网/Tailscale”扩展到**跨公网零配置开箱可用**，同时支持用户一键自托管；按 M6.2a（可选 TLS 过渡）→ M6.2b（盲转 E2EE 目标态）渐进交付。
- **前置条件**：M6.1 真机闭环通过。
- **分步子切片**：
  - **M6.2a（可选快速落地 · 传输层 TLS 中继）**：落地单二进制 Go 中继服务、Host Ed25519 质询注册、二进制分块与背压、客户端 `127.0.0.1` Loopback Gateway、服务端 `PeerLinks` 进程内 Relay Transport 与每设备独立撤销；链路基于 `wss://` TLS + T3 原生鉴权，UI 显式标明「传输层加密中继（非盲转 E2EE）」，优先面向自托管/受控中继场景快速验收跨公网能力。
  - **M6.2b（目标终态 · 零账号盲转 E2EE）**：在既有 `xtwork-relay/v1` 二进制帧与 `encryptionMode` 上开启标准 X25519 临时 ECDH + Ed25519 双向 transcript 认证 + AEAD + 严格递增 counter 防重放，同步补齐 CF Workers DO 参考实现（绑定自定义域名），达成中继全程零明文盲转。
- **代码边界**：
  - **独立中继与核心包（如 `relay/`）**：纯标准库/WebCrypto 协议核心、单二进制 Go 中继服务（Docker/systemd 一键部署 + 限流/配额）与 CF Workers DO 参考实现。
  - **被控端与控制端集成**：被控端服务端监管出站 Relay Agent（仅在用户开启「允许跨公网中继连接」时启动，Host Ed25519 私钥存于 OS SecretStore `app.xtwork.cross-device`）；控制端 mygo/本地网关起按环境隔离的 `127.0.0.1` Loopback Gateway 接入 `ConnectionDriver`（与 LAN/Tailscale 自动 500ms 竞速）；控制端服务端 `PeerLinks` 接入进程内 Relay Transport（逻辑地址 `xtwork-relay://...`）。
  - **前端 UI**：在「跨设备互联」卡片中增加“跨公网中继开关”“自定义中继 URL 输入框”“当前传输安全级别徽标（直连 / 盲转 E2EE / TLS 中继）”“一次性配对二维码/URI 展示与扫描/粘贴”“每台控制设备独立撤销列表”。
- **退出门禁（真机跨公网实测）**：
  1. 两台分处不同 NAT 后的电脑（含中国大陆网络环境）**零账号**扫码/粘贴 Pairing URI 30 秒内建连；M6.2a 验收 `wss://` 强制与 UI 诚实提示，M6.2b 抓包确认中继全程仅见密文与路由元数据，无法读取正文或伪造宿主；
  2. 恶意客户端仅持 `routingToken` 尝试注册 `/agent` 被质询验签拒绝，合法宿主不被踢下线；M6.2b 重放旧帧立即断连；在被控端撤销单台控制设备后，该设备 5 秒内断流且重连被拒，其他已配对设备不受影响；
  3. 经中继完成 **50 MiB 文件上传**、**连续 15 分钟 iOS 模拟器 AVCC/MJPEG 实时流 + 输入交互**（内存无持续上涨、无全量缓冲假死）以及**跨机 `PeerLinks` 委派与取消**；
  4. 切换自定义自托管 Go 中继地址后全链路通过，且关闭中继开关后零残留出站连接。
- **明确不做**：不引入用户账号/登录体系、不做 WebRTC 经中继 TURN 转发、不引入 `iroh`。

### M6.3 · mygo 壳远程两阶段桌面更新 + 跨平台补齐

- **目标**：补齐“在电脑 A 一键远程更新电脑 B 上的小瞳 Work 桌面版”，并按 `Q-12` / `Q-15` 补齐多平台控制端形态。
- **前置条件**：M6.1 或 M6.2 至少一条远程路由已通过真机验收，且 M5 签名发布源与更新清单已稳定（[09 品牌与发布](09-品牌与发布.md)）。
- **代码边界**：
  - **`shell/backend.go` 与 `shell/updates.go`**：
    - **POSIX（macOS / Linux）**：通过 Go `ExtraFiles` 向 Node 服务端传入 `desktopTelemetryFd`（fd 4）与 `desktopTelemetryControlFd`（fd 5），按上游 `DesktopTelemetryReceiver.ts` NDJSON 协议双向回报更新状态并承接 `requestDesktopUpdate` / `commitDesktopUpdate` / `cancelDesktopUpdate`；服务端重连与重启时自动重建绑定；
    - **Windows**：实现与上述 NDJSON 语义完全等价的命名管道 / loopback 私有控制通道适配器（避免依赖 POSIX `ExtraFiles`）。
  - **前端与权限**：在「跨设备互联」卡片中仅对拥有 `environment:maintain` 权限的远端环境显示更新状态与按钮；遵循两阶段 handoff（prepare 下载校验完毕 → 弹窗显式确认 → commit 重启并按 `requestId` 追踪重启后版本核验），记录更新审计日志。
  - **跨平台扩展（受 `Q-12` / `Q-15` 约束）**：按产品需求独立排期验收 **Linux（含 Omarchy）mygo WebKitGTK 桌面包** 及/或**无头服务端 CLI 后台服务（`boot-service` 模式）**，用于 Linux 工作站互控或远程开发机常驻。
- **退出门禁**：
  1. 从机器 A 向机器 B（macOS）发起远程更新：完成版本检查 → 下载校验（校验失败时保留旧版并清晰报错）→ 二次确认 → 机器 B 重启生效 → 机器 A 自动重连并确认新版本号；
  2. 无 `environment:maintain` scope 的只读/普通操作控制端尝试调用更新接口被服务端拒绝；
  3. 机器 B 正在运行未完成对话时，更新重启遵循既有优雅停机与恢复语义，不产生僵尸进程。

### M6.4 · 可插拔身份控制面（Identity Adapter）+ 机器共享与远期 P2P 评估

- **目标**：在不破坏“零账号开箱即用”的前提下，为多设备重度用户和企业客户提供**账号下自动发现设备**与**团队内按项目受控共享机器**能力。
- **前置条件**：M6.2 中继稳定运行，且有明确的多设备自动发现或团队共享交付诉求。
- **设计边界**：
  - **可插拔 `IdentityAdapter` 抽象**：定义统一接口（`authenticateUser`、`registerEnvironment`、`listDevices`、`issueEnvironmentCredential`、`discoverRoutes`、`revokeDevice`、`revokeLink`）。
    - Mode 0（默认）：关闭身份控制面，继续零账号配对；
    - Mode 1（面向外部个人/团队）：支持 **Passkey / 邮箱 / 通用 OIDC**；
    - Mode 2（企业交付插件）：把既有**企业微信 OIDC**、飞书、Azure AD 等作为平级可选 Adapter 接入，绝不污染核心协议。
  - **借鉴 Lody 的高阶安全增强**：
    - 账号级配对仍采用“新设备 128-bit 带外秘密二维码 + 老设备核验公钥摘要”防控制面篡改；
    - 引入**按项目机器共享策略**（机器默认私有，仅机器主人可按项目授权给团队成员；机器移除重绑生成新 `generation`，旧授权与在途请求全部失效）；
    - 为跨机 `PeerForwarding` 补齐签名执行意图信封（绑定操作者、源/目标环境、操作、参数与 `requestId`）；
    - 若开放受保护领航员/IM 跨机任务转发，必须满足 [ADR-013 §6](../decisions/013-leader-supervisory-threads.md#6-明确排期延后的能力受上述已定安全契约约束) 硬不变量（目标机须可验证并执行同等按 run fail-closed 策略）。
  - **远期 P2P 加速评估（可选）**：仅在真实跨公网延迟与中继带宽数据证明有必要时，再独立评估是否引入基于 QUIC 打洞（如 Go 原生 QUIC/Tailscale tsnet 或 `iroh`）的可选加速路由；绝不将其作为全平台硬依赖。
